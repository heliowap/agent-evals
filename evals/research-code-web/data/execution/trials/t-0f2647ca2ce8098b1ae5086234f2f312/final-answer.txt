## The three v4 classic tests

All three live in `packages/zod/src/v4/classic/tests/transform.test.ts` and build on the same `z.number()` → `String(n)` shape.

**1. Synchronous transform in an object — `test("coercion", …)`, lines 93–102.**
`numToString = z.number().transform((n) => String(n))` (line 94), then `z.object({ id: numToString }).parse({ id: 5 })` (lines 95–99). The only assertion is `expect(data).toEqual({ id: "5" })` (line 101) — the object's `id` is the string `"5"`, compared with `toEqual` (own-enumerable equality, not identity/strictness).

**2. Asynchronous transform via asynchronous parsing — `test("async coercion", …)`, lines 104–113.**
`numToString = z.number().transform(async (n) => String(n))` (line 105), then `await z.object({ id: numToString }).parseAsync({ id: 5 })` (lines 106–110). Assertion: `expect(data).toEqual({ id: "5" })` (line 112) — identical expected value, but reached through `parseAsync`.

**3. Asynchronous transform via synchronous parsing — `test("sync coercion async error", …)`, lines 115–125.**
`asyncNumberToString = z.number().transform(async (n) => String(n))` (line 116), then `expect(() => z.object({ id: asyncNumberToString }).parse({ id: 5 })).toThrow();` (lines 117–123). The assertion is a **bare `.toThrow()`**, and line 124 is a commented-out `// expect(data).toEqual({ id: '5' });`.

## Core runtime check that explains synchronous rejection

The classic entry point delegates straight to core: `z.object(...).parse(...)` calls `parse.parse(this, data, params, …)` (`packages/zod/src/v4/classic/schemas.ts:297–298`), and classic `parse` is `core._parse(ZodRealError)` (`packages/zod/src/v4/classic/parse.ts:13`; async twin at line 20). In `core._parse` (`packages/zod/src/v4/core/parse.ts:22–37`) the sync context is forced with `async: false` (line 24), the schema runs (line 25), and then `if (result instanceof Promise) { throw new core.$ZodAsyncError(); }` (lines 26–28).

More directly, the transform's own `_zod.parse` (`packages/zod/src/v4/core/schemas.ts:3844–3864`) invokes the callback (line 3849); if `ctx.async` is falsy and the callback returned a `Promise` (`_out instanceof Promise`), it throws `new core.$ZodAsyncError()` (lines 3856–3860). The error class is defined at `packages/zod/src/v4/core/core.ts:166–170`, `extends Error`, with message `Encountered Promise during synchronous parse. Use .parseAsync() instead.` (line 168). So the effective mechanism is an `instanceof Promise` guard on the async callback's return value, plus the same guard on the object result bubbling up through `_parse`.

## Does the rejection test assert an exact error class or message?

**No.** Test 3 uses `.toThrow()` with no argument (line 123), so it asserts only *that* something is thrown. It does **not** assert `$ZodAsyncError`, nor the message string, nor that the thrown thing is a particular class. The class name and exact text at `core.ts:166–170` are recoverable only by reading the runtime source — that is **static implementation inference**, not something the test pins down.

## Separating assertion from inference, and unresolved behavior

- **Directly asserted (evidence):** `{ id: "5" }` for the sync transform (line 101); `{ id: "5" }` for the async transform via `parseAsync` (line 112); "throws" (unspecified) for the async transform via sync `parse` (line 123).
- **Static inference only:** the identity of the thrown error (`$ZodAsyncError`, `core.ts:166–170`) and its message; the `async: false` → `instanceof Promise` → throw chain (`parse.ts:24–28`, `schemas.ts:3856–3860`).
- **Unresolved / not covered by these tests:** the guard is an `instanceof Promise` check, so *thenable* objects that are not real `Promise` instances (or a non-`async` function returning a promise) are a different case; the compiler path even comments that "a promise-returning callback that is not declared async compiles to a throw" (`parse.ts:180`), and uses a thenable-style `typeof result.then === "function"` test elsewhere (`compile.ts:313`). Nothing in these three tests exercises conditional/`MaybeAsync` return values, rejection payload contents, or whether the object-level or transform-level guard fires first. Those behaviors remain unverified by the cited assertions; I did not run any code or tests.
