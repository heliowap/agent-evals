## Assessment for Requests 2.31.0

**Yes — CVE-2024-35195 applies to this exact pattern.** The maintainer advisory, [GHSA-9wx4-h78v-vm56](https://github.com/psf/requests/security/advisories/GHSA-9wx4-h78v-vm56), lists affected versions as `< 2.32.0` and patched version as `2.32.0`; Requests 2.31.0 is therefore affected. The advisory describes precisely the scenario asked about: “When making requests through a Requests `Session`, if the first request is made with `verify=False` to disable cert verification, all subsequent requests to the same origin will continue to ignore cert verification regardless of changes to the value of `verify`.”

**Does the later `verify=True` reliably restore verification? No, not in 2.31.0.** A `Session` reuses connections from its pool, and in 2.31.0 the pool selection did not account for TLS/verification settings. The fixing change, PR [#6655](https://github.com/psf/requests/pull/6655), is titled “Use TLS settings in selecting connection pool,” and its description states: “Previously, if someone made a request with `verify=False` then made a request where they expected verification to be enabled to the same host, they would potentially reuse a connection where TLS had not been verified.” The PR’s regression test performs `s.get("https://invalid.badssl.com", verify=False)` followed by `s.get("https://invalid.badssl.com")`, expecting `requests.exceptions.SSLError` after the fix — i.e., before the fix, the second request could silently reuse the unverified connection and no fresh certificate-verifying handshake occurred. In 2.31.0, therefore, the second `verify=True` request does not force verification as long as the pooled `verify=False` connection remains reusable. If the old connection happens to have been closed or evicted by the server/pool, a new connection would be verified, but callers cannot rely on that; the advisory’s wording is categorical (“will continue … regardless”). In 2.32.0, TLS settings are incorporated into pool selection, so `verify=False` and `verify=True` get distinct pools and the second flag works.

**How long can the problematic behavior persist?** The advisory states: “This behavior will continue for the lifecycle of the connection in the connection pool.” It is not limited to one subsequent request. The unverified TLS state belongs to the pooled connection and can be reused across many later requests to that origin until that connection is closed or evicted, or the `Session` is closed. No fixed timeout is stated, and a long-lived keep-alive `Session` can retain it for a correspondingly long and nondeterministic period. That is why the advisory’s remediation explicitly addresses clearing the pool.

**Minimum patched release stated by the maintainer advisory:** `2.32.0`. The advisory’s “Patched versions” field says `2.32.0`, and its first remediation option is “Upgrade to `requests>=2.32.0`.” Separately, external trackers note that 2.32.0 (and 2.32.1) were yanked from PyPI due to regressions, with 2.32.2/2.32.3 later released ([Ubuntu security tracker](https://ubuntu.com/security/CVE-2024-35195); [Snyk](https://security.snyk.io/vuln/SNYK-PYTHON-REQUESTS-6928867)). That does not change the advisory-stated minimum: the minimum patched release is **2.32.0**, though a practical upgrade should select a non-yanked fixed release such as 2.32.2 or later.

**One advisory-documented mitigation for an installation that cannot yet upgrade:** “For `requests<2.32.0`, call `close()` on `Session` objects to clear existing connections if `verify=False` is used.” The advisory’s alternative is to avoid setting `verify=False` for the first request to a host while using a `Session`. In practice, either keep unverified requests out of a Session that will later make verified requests to the same origin, or close the Session to discard the unverified pooled connection before relying on `verify=True`.

**Limitations:** The advisory gives no wall-clock duration — actual persistence depends on server keep-alive, urllib3 pooling/eviction, proxies, and whether the specific pooled connection is reused. The yank details come from vendor/tracker search evidence rather than the advisory itself; direct PyPI metadata could not be retrieved within the available evidence budget.
