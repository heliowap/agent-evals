## Trace of `z.string().transform(fn)` in the v4 classic API (static analysis only)

### 1. Public builder → pipe construction (classic)

- On the shared `ZodType` prototype, `.transform()` is defined at **`packages/zod/src/v4/classic/schemas.ts:245-247`**:
  ```ts
  transform(tx) {
    return pipe(this, transform(tx));
  }
  ```
  So `z.string().transform(fn)` does **not** mutate the string schema; it builds a wrapper schema.
- The free function `transform<I, O>(fn)` (**classic/schemas.ts:2291-2298**) returns `new ZodTransform({ type: "transform", transform: fn })` — the user function is stored in the definition.
- The free function `pipe(in_, out)` (**classic/schemas.ts:2555-2566**) returns `new ZodPipe({ type: "pipe", in: in_, out: out })`.
- `ZodString` itself is constructed via `core.$ZodString.init(inst, def)` plus `_ZodString.init(inst, def)` (**classic/schemas.ts:529-533**), and the `string()` factory delegates to `core._string(ZodString, params)` (**classic/schemas.ts:619-620**).

**Representation:** the transformation is a `ZodPipe` whose `def.in` is the string schema and whose `def.out` is a `ZodTransform` (`type: "transform"`) wrapping the user function.

### 2. Core execution (core/schemas.ts)

- `$ZodPipe`'s constructor (**`packages/zod/src/v4/core/schemas.ts:4425-4447`**) installs `inst._zod.parse` (**4432-4446**). Forward direction: `const left = def.in._zod.run(payload, ctx)` (**4441**), then `handlePipeResult(left, def.out, ctx)` (**4445**; the `Promise` branches at 4442-4443 are skipped for a synchronous string + sync fn).
- **Order:** input parsing/validation of the string runs **first** (`def.in._zod.run`); the transformation runs **only afterward**, when `handlePipeResult` invokes `next._zod.run({ value: left.value, issues: left.issues }, ctx)` (**core/schemas.ts:4456**), and the transform's parse calls `def.transform(payload.value, payload)` — evidenced at **core/schemas.ts:3849** (`const _out = def.transform(payload.value, payload)`) and in the classic `ZodTransform` parse at **classic/schemas.ts:2278**, with the same `payload.value = output; return payload` pattern at **classic/schemas.ts:2285-2286**.
- **Which issues stop the pipe:** `handlePipeResult` (**core/schemas.ts:4449-4457**) aborts when *any* issue is present:
  ```ts
  if (left.issues.some((iss) => iss.code !== "unrecognized_keys")) {
    left.aborted = true;
    return left;
  }
  ```
  So every input issue halts the pipe and the transform never runs — **except issues with code `"unrecognized_keys"`**, the documented exception (**4450-4451**): the comment explains they describe the input's extra properties rather than the value being piped, and an enclosing intersection may still reconcile them. Those carried `unrecognized_keys` issues survive into the next run (they are passed via `issues: left.issues`, **4456**).
- **How the transformed value carries onward:** the transform writes its result back into the payload (`payload.value = output`, **classic/schemas.ts:2285-2286**), and the pipe hands that `left.value` to the next schema's run as `{ value: left.value, issues: left.issues }` (**core/schemas.ts:4456**). Statically, the pipe's output type is the out schema's output: `$ZodPipeInternals extends $ZodTypeInternals<core.output<B>, core.input<A>>` (**core/schemas.ts:4411-4412**), with `$ZodTransformInternals<O, I>` (**3828-3829**) supplying `O` — so `parse`/`safeParse` on the pipe resolve to the transformed value as the pipe's `_zod.output`.
