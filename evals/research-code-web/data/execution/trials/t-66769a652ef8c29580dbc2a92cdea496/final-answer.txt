## Assessment

**Does CVE-2024-35195 apply to Requests 2.31.0 in this scenario? Yes.**

The advisory covers all versions of `requests` before 2.32.0 (GitHub Advisory DB records affected versions `< 2.32.0`, patched `2.32.0`; OSV records "Introduced: 0, Fixed: 2.32.0"). Requests 2.31.0, with its first same‑origin request sent using `verify=False`, matches the affected configuration exactly. The issue is explicitly scoped to reuse within one `Session` against the same origin.

**Does the later `verify=True` reliably restore certificate verification? No.**

The maintainer's advisory states: "if the first request is made with `verify=False` to disable cert verification, all subsequent requests to the same origin will continue to ignore cert verification regardless of changes to the value of `verify`." The reason given is connection reuse: "the underlying connection is reused from the session's connection pool, causing the initial TLS verification setting to persist for the lifetime of the pooled connection." In other words, the second call reuses the already‑established (unverified) TLS connection, so the `verify=True` argument does not force a fresh verified handshake. The `verify` value is only applied when a new connection is actually built.

The upstream fix confirms the mechanism. PR #6655 ("Use TLS settings in selecting connection pool", merged 2024‑03‑11 by sigmavirus24) introduced `_urllib3_request_context(request, verify)` returning pool kwargs that include `cert_reqs` (`CERT_NONE` when `verify is False`, otherwise `CERT_REQUIRED`), and changed `send()` to call `self._get_connection(request, verify, proxies)` instead of `get_connection(request.url, proxies)` — i.e., it makes TLS settings part of how the connection pool is selected. The accompanying test `test_different_connection_pool_for_tls_settings` asserts that after `s.get("https://invalid.badssl.com", verify=False)`, a plain `s.get(...)` raises `requests.exceptions.SSLError`, demonstrating that verification is restored only once TLS settings select a different pool. Before that fix, a single pool served both settings, so `verify=True` could not reliably restore verification.

**How long can the problematic behavior persist?**

As long as the pooled connection survives. The advisory says the behavior "will continue for the lifecycle of the connection in the connection pool"; the advisory database phrasing is "for the lifetime of the pooled connection." It is therefore not limited to the immediately following request — any later request in that `Session` to that origin that reuses the same keep‑alive connection also skips verification. It ends when that connection is torn down or reset (e.g., the server closes it, the pool drops it, or the session is closed), not after a fixed number of requests or any time interval. Practically, that can be very long, since HTTP keep‑alive/connection reuse is designed to persist.

**Minimum patched release stated by the maintainer advisory: `requests` 2.32.0.**

The maintainer advisory lists "Patched versions: 2.32.0" and remediation "Upgrade to `requests>=2.32.0`." The changelog's 2.32.0 (2024‑05‑20) "Security" entry documents the fix and links the advisory. (The maintainer's stated minimum is 2.32.0; I am not substituting a later release. Note only as context: versions 2.32.1–2.32.2 followed quickly, and 2.32.2 renamed `_get_connection` to `get_connection_with_tls_context` for custom adapters.)

**Advisory‑documented mitigation if you cannot upgrade to 2.32.0:**

"For `requests<2.32.0`, avoid setting `verify=False` for the first request to a host while using a Requests `Session`." (A second documented option is to "call `close()` on `Session` objects to clear existing connections if `verify=False` is used.")

**Limitations:** I relied on the maintainer advisory, the GitHub Advisory Database entry, the PR #6655 diff/test, and the project changelog; I did not independently reproduce the behavior against a live origin, and the documented upper bound on persistence ("lifecycle/lifetime of the pooled connection") is qualitative rather than a fixed duration. One widely repeated claim that 2.32.0 was yanked comes from a non‑primary aggregator, so I did not rely on it.
