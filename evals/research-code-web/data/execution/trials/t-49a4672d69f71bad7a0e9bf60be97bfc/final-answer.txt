## Answer: No — the claim is false, and the decisive branch is explicit

In the snapshot's federation serializer (`web/federate.go`), not every selected native histogram can be emitted in every negotiated format. There is a closed skip branch that deliberately drops native histograms in certain formats.

**The decisive closed skip branch: `web/federate.go:191-203`**

At the top of the per-sample emit loop, the serializer computes `isHistogram := s.H != nil` (line 191) and then:

```go
if isHistogram &&
    !s.H.UsesCustomBuckets() &&
    formatType != expfmt.TypeProtoDelim &&
    formatType != expfmt.TypeProtoText &&
    formatType != expfmt.TypeProtoCompact {
    // Can't serve a native histogram with a non-protobuf format.
    // (We can serve an NHCB, though, as it is converted to a
    // classic histogram for federation.)
    // TODO(codesome): Serve them when other protocols get the native histogram support.
    continue
}
```

This is a `continue` — a closed skip: the sample path never reaches label validation or `enc.Encode` for such samples.

**Format categories permitted for histograms *without* custom buckets**

The negotiated format set is defined at `web/federate.go:75`: the four candidates are `TypeProtoDelim`, `TypeProtoText`, `TypeProtoCompact`, and `TypeTextPlain`. Given the guard's negated conditions, a non-custom-bucket native histogram passes the guard only for the three **protobuf categories** (protobuf delimited, protobuf text, protobuf compact). The sole non-protobuf category among the negotiated candidates — `TypeTextPlain` (plain text exposition) — fails all three negated format checks, so those histograms are silently skipped with no error or metric increment. A comment confirms intent: "Can't serve a native histogram with a non-protobuf format" (line 198). Consistently, `makeNativeHistogram` (lines 315-346) is documented as "Use only for standard exponential schemas" and builds a native `dto.Histogram` (schema, zero threshold, spans, integer-style buckets).

**Contrast: custom-bucket (NHCB) histograms**

For histograms where `UsesCustomBuckets()` is true (NHCB, schema −53), the guard is a no-op — all of its conjuncts must hold to skip, and `!s.H.UsesCustomBuckets()` is false. Their exemption is explicitly commented: "We can serve an NHCB, though, as it is converted to a classic histogram for federation" (lines 199-200). At emission, `web/federate.go:297-298` routes them through `makeClassicHistogram`, which (lines 348-378) constructs a classic cumulative-bucket `dto.Histogram` from `CustomValues` and the positive bucket iterator — no native schema/spans fields. Because it becomes a classic histogram in the protobuf DTO, the generic protobuf→payload conversion (including the plain-text path, which adds the +Inf bucket per the note at lines 373-376) can render it in any negotiated format. So the protobuf-only restriction does **not** apply to custom-bucket histograms.

**Does the restriction apply to ordinary float samples? No.**

The guard's first conjunct is `isHistogram` (line 193, derived from line 191). For ordinary float samples `s.H` is nil, so the entire branch is short-circuited and never skipped; they proceed to the `Untyped` payload at lines 290-294 regardless of negotiated format. The staleness filter at lines 144-150 (`value.IsStaleNaN(f)` / `fh.Sum`) is orthogonal and applies to both kinds, but it is a different branch (lines 148-150).

**Caveat / unresolved limitation**

All above is read straight from `web/federate.go` in the snapshot; I did not inspect the vendored `github.com/prometheus/common/expfmt` encoder internals, so whether any protobuf format degenerates at the library level is outside this evidence — but within the serializer itself the gating logic above is authoritative. Also, `docs/federation.md:9` mentions native-histogram federation support in a note, which is consistent with the protobuf-gated behavior found in the code.
