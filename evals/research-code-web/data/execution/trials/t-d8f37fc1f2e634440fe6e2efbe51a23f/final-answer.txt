## Short answer: audioop

| Question | Answer | Basis |
|---|---|---|
| Deprecation release | **Python 3.11** | PEP 594 Table 1; 3.12 docs banner "Deprecated since version 3.11" |
| Actual removal release | **Python 3.13** | "What's New In Python 3.13"; current docs stub |
| Last Python release that included it | **Python 3.12** (the final 3.12.x) | PEP 594 schedule; 3.12 docs still document it |
| Governing PEP | **PEP 594**, *Removing dead batteries from the standard library* (Status: Final; Python-Version: 3.11) | PEP 594 itself |

Primary sources agree. PEP 594's Table 1 lists `audioop` as "Deprecated in 3.11 (3.0\*)", "To be removed 3.13", added 1992. The 3.12 library reference still carries the full module documentation, headed: "Deprecated since version 3.11, will be removed in version 3.13: The `audioop` module is deprecated (see PEP 594 for details)", followed by all its functions (`add`, `adpcm2lin`, `byteswap`, `lin2adpcm`, etc.). "What's New In Python 3.13" states that "The remaining 19 'dead batteries' … have been removed from the standard library: `aifc`, `audioop`, `cgi`, …". The current documentation page for `audioop` now reads: "Deprecated since version 3.11, removed in version 3.13. This module is no longer part of the Python standard library. It was removed in Python 3.13 after being deprecated in Python 3.11. The removal was decided in PEP 594."

## Checking the migration note

The note contains three claims; only the first survives scrutiny.

1. **"Deprecated in Python 3.11" — correct.** PEP 594's 3.11 section: "Starting with Python 3.11, deprecated modules will start issuing `DeprecationWarning`."

2. **"Already absent from Python 3.12's standard library" — false.** PEP 594's 3.12 section says: "There should be no specific change compared to Python 3.11. This is the last version of Python with the deprecated modules." The 3.12.15 documentation still ships the complete `audioop` page. So 3.12 both included and deprecated it. Any inference to the contrary would rest on a missing page rather than positive evidence of removal — and here the page demonstrably exists, so that inference is invalid.

3. **"Every module discussed by PEP 594, including optparse, was removed in 3.13" — false twice over.** PEP 594 does not remove every module it *discusses*. Its "Modules to keep" section states: "Some modules were originally proposed for deprecation but are no longer listed as such in this PEP," and Table 2 ("Withdrawn deprecations") lists `colorsys`, `fileinput`, `getopt`, `optparse`, and `wave`. Also, not all removals happened in 3.13: `asynchat`, `asyncore`, and `smtpd` (deprecated 3.6 / 3.4.7;3.5.4) were targeted for and removed in 3.12.

## optparse separately

Despite its **historical** deprecation, optparse was explicitly retained by PEP 594. Table 2 records it as a *withdrawn* deprecation — "optparse | 3.2 | argparse" — meaning its old deprecation (since 3.2, where argparse was the recommended replacement) was not acted upon by this PEP. The PEP's rationale reinforces the keep decision: "The optparse and getopt modules are widely used. They are mature modules with very low maintenance overhead."

This is corroborated by the live documentation: `optparse` remains a fully documented standard-library module in the current (3.14.8) docs, filed under "Command-line interface libraries," with a companion page "Migrating optparse code to argparse." So an accurate read is: optparse is *soft-deprecated/unmaintained* in favour of argparse, but PEP 594's explicit decision was to **keep**, not remove, it — it is unaffected by the 3.13 removals.
