## Short answer

**At launch (Node.js 22.0.0, 2024‑04‑24)** the feature was behind a CLI flag: `--experimental-require-module`. The launch announcement's section "Support require()ing synchronous ESM graphs" states: "This release adds `require()` support for synchronous ESM graphs under the flag `--experimental-require-module`," applying when the module is "Explicitly marked as an ES module with a `"type": "module"` field in the closest package.json or a `.mjs` extension" and is "Fully synchronous (contains no top-level await)," in which case `require()` "will load the requested module as an ES Module, and return the module name space object," and "We intend to eventually enable `require(esm)` by default in the future, without the flag." (source: https://nodejs.org/en/blog/announcements/v22-release-announce)

**In Node.js 22.12.0 "Jod" (LTS), 2024‑12‑03**, the flag is gone from the 22.x line: "Support for loading native ES modules using `require()` had been available on v20.x and v22.x under the command line flag `--experimental-require-module`, and available by default on v23.x. In this release, it is now no longer behind a flag on v22.x." The corresponding commit is listed as `58d6871c45` — "(SEMVER-MINOR) module: unflag --experimental-require-module (Joyee Cheung) #55085" (source: https://nodejs.org/en/blog/release/v22.12.0).

**Does "enabled by default" mean stable? No.** The same 22.12.0 release post explicitly says: "This feature is still experimental, and we are looking for user feedback to make more final tweaks before fully stabilizing it." The release notes also include the docs commit `f1b9791694` "doc: update `require(ESM)` history and stability status (#55199)," i.e. the stability labelling was being revised while the feature remained non-stable. So on exactly 22.12.0 there is a deliberate split: on-by-default, but not stable.

**Top-level await error:** with the feature enabled, `require()` "will no longer throw `ERR_REQUIRE_ESM` … It can, however, throw `ERR_REQUIRE_ASYNC_MODULE` if the ES module being loaded or its dependencies contain top-level `await`." The v22.12.0 API docs make the same point from the other side: "The CommonJS module `require` currently only supports loading synchronous ES modules (that is, ES modules that do not use top-level `await`)." (https://nodejs.org/docs/v22.12.0/api/esm.html)

**Disabling flag (22.12.0):** `--no-experimental-require-module`, described in the 22.12.0 notes as the workaround — "this feature can also be disabled using `--no-experimental-require-module`."

**Runtime feature check documented for 22.12.0:** `process.features.require_module` — "Users can check `process.features.require_module` to see whether `require(esm)` is enabled in the current Node.js instance." For packages, the companion check is the `"module-sync"` exports condition, which (per the v22.10.0 notes, where it and the process feature landed via `111261e245` #54648 and `e95163b170` #55241) "is enabled when `require(esm)` is enabled," letting both `require()` and `import` load the same native ES module.

Reconciliation: the two documents are consistent in mechanism (same flag, same synchronous-graph restriction, same namespace-object return) but differ in *default state* — 22.0.0 shipped it opt-in behind `--experimental-require-module` with the stated intent to unflag it, and 22.12.0 executed that intent as a semver-minor unflagging while keeping experimental status.

## Unresolved limitations

- Exact wording/number of the stability index in the v22.12.0 docs for `require(esm)` could not be verified: my fetch attempts against `docs/v22.12.0/api/esm.html` overshot the page (it is only ~34,864 normalized characters) and the `modules.html` tail slice was consumed by the evidence-budget cap before reaching the "Loading ECMAScript modules using require()" text. The "still experimental" conclusion rests on the 22.12.0 release post.
- The live blog text of the 22.12.0 announcement says the first-use experimental warning applies "on v23.x," whereas the GitHub changelog/release-proposal wording (PR #56040) says "on v22.x"; I did not retrieve the underlying commit diff to resolve which phrasing is authoritative for the 22.x branch.
- All findings above are deliberately confined to 22.0.0 and 22.12.0 (plus 22.10.0 for the feature-detection additions); no later release's behavior (e.g. 23.x/24.x stabilization) is used.
