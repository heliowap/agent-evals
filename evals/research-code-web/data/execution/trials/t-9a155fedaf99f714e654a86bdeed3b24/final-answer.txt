## Answer

Everything below comes from the Kubernetes v1.34 documentation snapshot of the Version Skew Policy (kubernetes.io/v1-34/releases/version-skew-policy/), which is the version-specific primary source requested. I am deliberately ignoring that page's "Supported versions" section (the three-release maintenance window) because you asked to apply only the version-skew policy, not release-support or vendor policy.

### General client/server minor-skew rule

The policy states plainly: "`kubectl` is supported within one minor version (older or newer) of `kube-apiserver`." In formal terms, if the API server is at minor *n*, supported kubectl is *n−1* through *n+1*. This is symmetric — kubectl may be one minor older **or** one minor newer than the server, unlike kubelet/kube-proxy (which must not be newer) and the control-plane managers (which must not be newer and may be one older). The same page also fixes the HA server rule: "the newest and oldest `kube-apiserver` instances must be within one minor version" of each other.

### Case 1 — all kube-apiserver instances at 1.34

The doc's worked example for exactly this case:

- kube-apiserver at **1.34**
- kubectl supported at **1.35, 1.34, and 1.33**

So kubectl 1.33, 1.34, and 1.35 are all permitted; 1.32 and 1.36 are not.

### Case 2 — HA upgrade with servers at 1.33 and 1.34

The page explicitly warns: "If version skew exists between `kube-apiserver` instances in an HA cluster, this narrows the supported `kubectl` versions." Its example:

- kube-apiserver instances at **1.34 and 1.33**
- kubectl supported at **1.34 and 1.33** ("other versions would be more than one minor version skewed from one of the kube-apiserver components")

The permitted intersection is therefore {1.33, 1.34}: each server independently requires a client within ±1 of its own minor, so take the overlap of {1.32, 1.33, 1.34} (for the 1.33 servers) and {1.33, 1.34, 1.35} (for the 1.34 servers) = {1.33, 1.34}.

**Is kubectl 1.35 supported during this window? No.** Against the 1.33 servers, 1.35 is two minors newer — outside the one-minor rule. The policy's narrowing note is the direct authority; the transient mixed-version state makes 1.35 unsupported until the old servers are gone.

### Reassessment after all servers reach 1.34

Once every kube-apiserver instance is at 1.34, the HA narrowing no longer applies and you are back to Case 1. kubectl **1.35 becomes permitted**, alongside 1.34 and 1.33. This is a genuine state change, not a change in the rule: the same one-minor-window rule is re-evaluated against the new, homogeneous server set. The v1.34 upgrade-order section confirms the transition is legitimate: an HA cluster may have API servers at "1.33 or 1.34" during the rollout, and once the upgrade completes all instances are 1.34.

### Caveats and limitations

- I applied only the v1.34 version-skew page. I did not apply release-support/maintenance windows (that page happens to list 1.36/1.35/1.34 as maintained branches, which is a separate policy you excluded), nor any vendor/distribution restriction.
- The page notes cluster deployment tools "may place additional restrictions on version skew"; such restrictions are out of scope here.
- The policy governs *support/compatibility*, not guaranteed bug-freeness; the doc additionally recommends keeping components on the latest patch of their minor.
- Patch versions (z) do not affect the minor-version result.
- Evidence is a single snapshot page fetched 2026 (© 2026 Kubernetes Authors); the v1.34 docs are a frozen static snapshot, so the text is stable, but I did not cross-check other v1.34 pages for identical phrasing.

**Bottom line:** general rule = kubectl within one minor older or newer than kube-apiserver (n−1…n+1). All servers 1.34 → kubectl 1.33/1.34/1.35. HA 1.33+1.34 → intersection 1.33/1.34, and 1.35 is *not* supported then. After all servers hit 1.34 → 1.35 becomes supported.
