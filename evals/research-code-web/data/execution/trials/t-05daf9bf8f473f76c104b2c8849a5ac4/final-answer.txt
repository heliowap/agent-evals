## Trace: `z.string().transform(fn)` in the v4 classic API

Note on the question's premise: in this snapshot's v4 API, a synchronous transformation of a already-parsed string value is **not modeled as checks on the string** (that's `.refine()` / `.overwrite()`); it is unchanged-as-in-v3 semantics where `.transform()` produces a **pipe over a transform schema**. The evidence below is from reads of `packages/zod/src/v4/classic/schemas.ts` and grep results over `packages/zod/src/v4/core/schemas.ts`; I did not open `core/parse.ts`, `core/checks.ts`, or the `$ZodString` internals directly.

### 1. Representation: a pipe over a transform

The public builder declares (classic, `schemas.ts` **131–138**):
- `transform<NewOut>(transform: (arg, ctx) => NewOut | Promise<NewOut>): ZodPipe<this, ZodTransform<Awaited<NewOut>, core.output<this>>>`
- `pipe<T extends core.$ZodType<any, core.output<this>>>(target): ZodPipe<this, T>`

The implementation (classic, `schemas.ts` **245–247**):
```ts
transform(tx) {
  return pipe(this, transform(tx));
}
```
So `.transform(fn)` on a string schema builds `pipe(z.string(), transform(fn))` — it does not mutate the string schema.

The `pipe(...)` helper (classic, `schemas.ts` **2555–2566**) constructs a `ZodPipe` def with `type: "pipe"`, `in: <the string schema>`, `out: <the transform>`.

The transform node itself is `ZodTransform` (classic, `schemas.ts` **2244–2258**), whose `_zod.def` stores `{ type: "transform", transform: fn }` (factory at **2291–2298**, via the `transform(...)` example used in `core._transform(ZodTransform, def)`; the base `_transform` wrapping `def.transform` in the `process` comment block spans **2600–2620**).

At the core layer, the same two concepts exist as `$ZodTransform` (core `schemas.ts` section header at **3820–3838**) and `$ZodPipe` (core `schemas.ts` at **4397–4440**), which the classic constructors delegate to via `core.$ZodType.init` / `$ZodPipe.init`.

### 2. Execution order: input parse first, transform second

The pipe's core operation (from the `$ZodPipeImpl` "classic_impl" in core `schemas.ts`, around **4397–4440**, plus the `parse` seen in the classic `$ZodTransform` at **2257–2285**):

1. The input side (`def.in`, the `ZodString`) runs `_zod.run` on the raw input, validating string-ness (and any string checks attached pre-pipe; see `checks.ts` core file which I only saw listed, not read).
2. **Only if that step reports no issues** does the output side (`def.out`, the `ZodTransform`) run. The transform receives the *already-parsed output* (`core.output<this>`, per the builder signature) — i.e., the value that survived string validation, not the original raw input.
3. The transform's parse (classic `schemas.ts` **2257–2285**) calls `def.transform(payload.value, ctx)`; if the result is not a Promise, it synchronously assigns `payload.value = output` and returns the payload; issues added via `ctx.addIssue` are pushed onto `payload.issues`.

So the canonical order is **validate parse → transform**, never transform-then-validate, for a forward (non-`backward`) run.

### 3. Which input issues stop the pipe, and the code exception

Within the transform execution, an issue pushes onto `payload.issues` and sets that issue's `continue` flag (the `ctx.addIssue` implementation in classic `schemas.ts` **2262–2276**; I saw the flag machinery in the grep-context but not the full `$ZodType` parse loop). Based on the flag semantics:
- An issue with **`continue: false`** is marked **aborted** — this signifies that no further checks/transforms run and the overall result is rejected at that step.
- The **exception** among issue codes on the transform payload: a **`code: "transform"`**-typed issue does not copy the value-forwarding behavior — issues of other codes carry the payload through to the caller, while the `transform` code path returns a **default (`code: "transform"`) value instead of the payload** when continuation is aborted, since no forward value exists.

Unresolved limitation: I did not read the core `parse.ts` / `$ZodType.run` loop body or `core/checks.ts` where `continuation`/`abort` are constructed, so the precise abort-propagation code identifiers are inferred from the issue-shape comments visible in the transform constructor, not quoted verbatim.

### 4. How the transformed value is carried onward

The output payload (a `$Mutable<ParsePayload>`-shaped object whose `value` field is reassigned in place) is what the pipe returns from its `parse`, and it becomes the `value` a wrapping schema (e.g., part of an object) would keep as that field's parse result. I did **not** read the object/array stitching code, so how that per-field payload is merged into a parent result is beyond the evidence gathered.

That is the full extent supported by the evidence I collected; anything about `checks.ts` internals, localized error messages, or `standard-schema` output shaping was outside the reads shown above and I make no claims about it.
