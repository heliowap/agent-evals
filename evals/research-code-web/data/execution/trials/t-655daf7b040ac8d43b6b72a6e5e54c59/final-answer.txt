## Assessment: CVE-2024-35195 and the verify=False → verify=True scenario

**Verdict: Yes, this exact scenario is the vulnerability described by CVE-2024-35195, and the second `verify=True` does *not* restore verification.**

### Does it affect Requests 2.31.0 in this scenario?

The maintainer advisory (psf/requests, GHSA-9wx4-h78v-vm56, published May 20, 2024 by nateprewitt) lists **affected versions `< 2.32.0`**, so Requests **2.31.0 is in the affected range** ([psf/requests advisory](https://github.com/psf/requests/security/advisories/GHSA-9wx4-h78v-vm56)). The scenario described — a `Session` whose *first* request to an origin uses `verify=False`, followed by a request to the *same origin* with `verify=True` — matches the advisory's trigger conditions precisely.

### Does the second flag reliably restore verification?

**No.** The advisory states: *"When making requests through a Requests Session, if the first request is made with verify=False to disable cert verification, all subsequent requests to the same origin will continue to ignore cert verification regardless of changes to the value of verify."* ([psf/requests advisory](https://github.com/psf/requests/security/advisories/GHSA-9wx4-h78v-vm56)). The GitHub Advisory Database/OSV rendering adds the mechanism and caveat: the underlying connection is reused from the session's connection pool, so *"TLS certificate verification may remain disabled for all subsequent requests to that origin, even if `verify=True` is explicitly specified later"* ([OSV record](https://osv.dev/vulnerability/GHSA-9wx4-h78v-vm56)). Practically, the second request proceeds on a TLS connection established without peer-certificate validation, with **no warning or error raised** to signal the bypass. The NVD/CVE record (CNA: GitHub, Inc.) uses the same wording and adds *"This vulnerability is fixed in 2.32.0"* ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2024-35195)).

### How long can the problematic behavior persist?

Per the maintainer advisory: *"This behavior will continue **for the lifecycle of the connection in the connection pool**"* ([psf/requests advisory](https://github.com/psf/requests/security/advisories/GHSA-9wx4-h78v-vm56)). So it is not transient or per-request: as long as that pooled connection stays alive (keep-alive connections in a long-lived `Session` can persist for the life of the process), every subsequent request to that origin silently skips certificate verification — even with `verify=True` explicitly set on each call. Because per-request flag changes never clear it, the only state resets documented are closing the Session's connections or upgrading.

### Minimum patched release stated by the maintainer advisory

**Requests 2.32.0** (released 2024-05-20). The advisory's "Patched versions" field is **2.32.0** and its remediation says *"Upgrade to `requests>=2.32.0`"* ([psf/requests advisory](https://github.com/psf/requests/security/advisories/GHSA-9wx4-h78v-vm56)). The project's release history confirms the fix entry: *"Fixed an issue where setting `verify=False` on the first request from a Session will cause subsequent requests to the same origin to also ignore cert verification, regardless of the value of `verify`"* ([HISTORY.md](https://raw.githubusercontent.com/psf/requests/main/HISTORY.md)). I am deliberately not characterizing the *latest* release (history shows later versions through 2.34.2 in 2026, and 2.32.5 reverted the SSLContext caching introduced by this fix). One caveat from a secondary source: Snyk notes 2.32.0 was yanked from PyPI, making 2.32.2 the next *available* fixed release — but the advisory's stated minimum patched version remains 2.32.0.

### Advisory-documented mitigation without upgrading

The advisory's remediation section offers two non-upgrade options; one is: *"For `requests<2.32.0`, **avoid setting `verify=False` for the first request to a host** while using a Requests Session."* The companion option: *"call `close()` on `Session` objects to clear existing connections if `verify=False` is used"* ([psf/requests advisory](https://github.com/psf/requests/security/advisories/GHSA-9wx4-h78v-vm56)).

### Limitations

- I did not run a live reproduction; the behavioral conclusions rest on the maintainer advisory's description (backed by the fix in #6655 and the 2.32.0 changelog).
- My direct fetch of the NVD detail page returned only the page shell; the NVD description text was obtained via the search pipeline, and it matches the CVE record sourced from GitHub, Inc.
- Upgrading also carries an API impact: 2.32.2's changelog notes custom `HTTPAdapter` subclasses must migrate to `get_connection_with_tls_context` to remain safe ([HISTORY.md](https://raw.githubusercontent.com/psf/requests/main/HISTORY.md)).
