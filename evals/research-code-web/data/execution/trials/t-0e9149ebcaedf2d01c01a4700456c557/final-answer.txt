## Tracing `z.string().transform(fn)` in the v4 classic snapshot

### 1. How the transformation is represented

**Public builder (classic).** `ZodType` declares `transform<NewOut>(...): ZodPipe<this, ZodTransform<Awaited<NewOut>, core.output<this>>>` (`packages/zod/src/v4/classic/schemas.ts:131-133`), and its implementation is `transform(tx) { return pipe(this, transform(tx)); }` (classic `schemas.ts:245-247`). So a string schema's transform is **not** a property of the string schema itself: it is represented as a **`ZodPipe`** whose `def.in` is the original `ZodString` and whose `def.out` is a standalone **`ZodTransform`** schema.

The two factories build that shape:
- `transform(fn)` returns `new ZodTransform({ type: "transform", transform: fn })` (classic `schemas.ts:2291-2298`).
- `pipe(in_, out)` returns `new ZodPipe({ type: "pipe", in: in_, out: out })` (classic `schemas.ts:2555-2566`).

The classic wrappers are thin: `ZodPipe` calls `core.$ZodPipe.init(inst, def)` and exposes `inst.in = def.in; inst.out = def.out;` (classic `schemas.ts:2546-2553`); `ZodTransform` calls `core.$ZodTransform.init` and then installs its own `inst._zod.parse` (classic `schemas.ts:2249-2289`).

### 2. Order of input parsing and transformation

Core `$ZodPipe` (`packages/zod/src/v4/core/schemas.ts:4425-4447`) defines the pipe's parse: in the forward direction it first runs the input side — `const left = def.in._zod.run(payload, ctx)` (core `schemas.ts:4441`) — i.e. the string schema's validation and any attached checks run **first**. Only then does it feed the result to the output side via `handlePipeResult(left, def.out, ctx)` (core `schemas.ts:4445`), which eventually invokes the user's function: `def.transform(payload.value, payload)` (core `schemas.ts:3849`; classic override classic `schemas.ts:2278`). So the order is strictly **parse-then-transform**; a failing input never reaches the transform (the comment at core `schemas.ts:4450` states "a failing refinement never feeds its transform").

### 3. Which issues stop the pipe, and the exception

`handlePipeResult` (core `schemas.ts:4449-4457`) is the gatekeeper:

- **Stop rule:** `if (left.issues.some((iss) => iss.code !== "unrecognized_keys"))` → the payload is marked `left.aborted = true` ("prevent further checks") and returned; the out/transform side is never run. **Any issue at all stops the pipe** — the `aborted` flag is described at core `schemas.ts:47-48` as "A way to mark a whole payload as aborted. Used in codecs/pipes."
- **Issue-code exception:** `"unrecognized_keys"`. Per the comment (core `schemas.ts:4450`): "An unrecognized key is the exception: it describes the input's extra properties, not the value being piped, and an enclosing intersection may yet reconcile it." Such issues do not abort, and the pipe continues.

(Backward direction, for completeness: both transforms throw `$ZodEncodeError` on `direction === "backward"` — classic `schemas.ts:2258-2260`, core `schemas.ts:3845-3847` — and the pipe runs `out` then `in` instead, core `schemas.ts:4433-4439`.)

### 4. How the transformed value is carried onward

The user function's return value is written back into the shared parse payload: `payload.value = _out; return payload;` (core `schemas.ts:3862-3863`; the classic `ZodTransform` parse does the same synchronously at classic `schemas.ts:2285-2286`, awaiting first if a Promise is returned, classic `schemas.ts:2279-2284`). In the pure synchronous path, a Promise result is rejected with `$ZodAsyncError` (core `schemas.ts:3858-3860`). `handlePipeResult` then passes the value onward by constructing a fresh payload for the next stage: `next._zod.run({ value: left.value, issues: left.issues }, ctx)` (core `schemas.ts:4456`) — the transformed value rides in the payload's `value` field, with tolerated issues (e.g. `unrecognized_keys`) carried alongside into the out stage, and the out stage's returned payload becomes the pipe's parse result propagating upward.

### Limitations

- I did not read core `parse.ts` or `$ZodType.init`/`_zod.run` internals, so the mechanics bridging `_zod.run` → `_zod.parse` and the final payload-to-`parse()` result mapping are inferred, not directly evidenced.
- `$ZodString`'s own parse/check internals were not inspected; the "checks run inside the `in` stage" claim rests on the pipe code and the `handlePipeResult` comment.
- No code or tests were run, per instructions.
