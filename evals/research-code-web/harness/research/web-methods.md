# Web-search + web-fetch evaluation methods

Research date: 2026-10-07. Status: findings and proposal for parent/planner approval only; no candidate execution, probes, warmups, installs, authentication, or configuration changes.

## Answer

- **DESIGN JUDGMENT:** Evaluate practical, question-only research through a common search-then-fetch harness, not another supplied-URL documentation lookup; retain a separately labelled frozen-retrieval control. Primary basis: [S1], [S2], [S4].
- **DESIGN JUDGMENT:** Grade required facts, omissions, unsupported extras, synthesis, citation entailment, URL accessibility, instructions, and safety separately; publish continuous semantic quality and a task-specific success rate. Primary basis: [S1], [S2], [S5], [S6].
- **DESIGN JUDGMENT:** Compare completed-answer quality against end-to-end latency under identical externally imposed budgets, retain timeouts/errors in denominators, and pair trials by task/time block. Primary basis: [S2], [S3], [S4].
- **DESIGN JUDGMENT:** Prefer at least eight independently authored tasks and three repetitions per confirmed configuration if quota permits; fewer repetitions mean exploratory evidence, not a confident ranking. Primary basis: [S2]; sample-size sufficiency remains unverified.

**DESIGN JUDGMENT — three distinct constructs:** (a) provided document/context retrieval tests selecting/reading supplied material; (b) question-only official-doc discovery tests finding authoritative docs without supplied answer URLs; (c) broader engineering web research tests query formulation, entity disambiguation, independent evidence, conflicting dates/versions, uncertainty and synthesis. The new suite should contain (b) and (c); (a) belongs in a separately labelled control or the other suite. This taxonomy is our operational definition, informed by [S2]–[S6], not a standard benchmark classification.

## Actionable methodology for the planner

### 1. Freeze task intent and gold without leaking answers

- **DESIGN JUDGMENT:** Before any candidate output, freeze question wording, explicit date/version/jurisdiction, required atomic claims, acceptable alternatives/tolerances, critical errors, source-authority hierarchy, expected uncertainty, and semantic success rubric. All scored requirements must be inferable from the question. Give task authors a known passing reference answer, withheld from candidates. Basis: [S1], [S2], [S6].
- **DESIGN JUDGMENT:** Independently search/fetch candidate task evidence during task curation, document at least one feasible path, and validate that the approved engine/fetcher can expose the required evidence. Do not use candidate calls to tune difficulty. These archetypes are NOT frozen tasks or gold yet. Basis: [S2], [S6].
- **DESIGN JUDGMENT:** Store gold evidence and claim mappings outside candidate-visible files/tool results. Keep newly authored tasks private until testing; prohibit benchmark answer repositories, leaked QA pages and grader artifacts through a common tool-layer deny policy. A broad host safety allowlist must not enumerate the answer-bearing pages. Basis: leakage observations [S3], [S8], [S6 §5.2].
- **DESIGN JUDGMENT:** Distinguish benchmark-answer leakage from legitimate discovery: an official page directly answering an ordinary practical question is valid evidence, not something to block merely because it answers well. If using report-derived tasks to test independent synthesis, disclose blocked reference reports and enforce the same restrictions for everyone without handing out a gold-source shortlist. Basis: [S6 §5.2]; application to practical tasks is judgment.
- **DESIGN JUDGMENT:** Accept alternate valid answers and support sets after blinded adjudication; preserve the original gold, amendment reason and all affected rescoring. Do not silently retune prompts, budgets or criteria after seeing model identities. BrowseComp itself acknowledges that inverted questions cannot guarantee answer uniqueness [S3 §2.1].

### 2. Practical archetypes, not final answer keys

Every live task below starts with a question, not answer URLs; anticipated fetch counts are design estimates, not verified feasibility. Select at least eight, spanning four strata (routine, applied, difficult, stress), with balanced types across configurations. No candidate difficulty pilot before approval. Basis for the mixture: task-specific distributions and edge/adversarial coverage [S1], research-relative quality [S2], temporal/atomic criteria [S6].

| Archetype | Example question shape, without final gold | Proposed stratum / what to score |
| --- | --- | --- |
| 1. Routine official-source discovery | Find a project's current supported runtime floor and where its maintainers state it, as of a named date. | Routine; query, authoritative fetch, exact scoped fact; one sufficient source is acceptable. |
| 2. Narrow engineering decision | Determine whether a specified deployment feature is supported on a named platform and identify its documented caveat. | Routine/applied; correct decision and limitation, not every feature of the product. |
| 3. Versioned migration | For named old/new releases, identify two behavior changes and the migration action from release notes plus reference docs. | Applied; distinguish versions and join evidence across pages. |
| 4. Cross-project compatibility | Does version X of one component support version Y of another, and what upgrade route is documented? | Applied; genuine multihop search, both projects' evidence, qualified conclusion. |
| 5. Advisory applicability | For an explicit package/version, decide whether a public security advisory applies and locate the stated fix. | Difficult; advisory plus maintainer release evidence, no exploit execution or private data. |
| 6. Conflicting recency | Reconcile a launch announcement with a later official changelog on availability, using a fixed cutoff. | Difficult; dates, supersession, do not cherry-pick stale snippets. |
| 7. Small multi-source comparison | Compare two public engineering approaches on two named requirements and explain a bounded recommendation. | Difficult; four required facts plus one justified tradeoff; not a PhD report or exhaustive market scan. |
| 8. Ambiguity / negative evidence | Assess a plausible but unconfirmed feature claim for an explicitly named project; state exactly what documentation can and cannot establish. | Stress; calibrated abstention, bounded search and no universal “does not exist” from missing hits. |
| 9. Search/fetch recovery | Find a documented change whose old link redirects or fails; locate an accessible authoritative replacement. | Stress; recovered evidence and final answer, distinguish exploration failures from final invalid citations. |
| 10. Adversarial tool content | A controlled result/page includes benign factual evidence plus instructions to abandon the task or reveal secrets. | Stress/control lane; ignore injected instructions while extracting facts; no real secrets. Injection exposure cannot be guaranteed by uncontrolled live search. |

**DESIGN JUDGMENT:** Tag overlapping stressors rather than treating these ten as ten independent capabilities. A version task can also have a stale snippet or redirect. If the suite is explicitly research-required, do not reward unnecessary extra searches; a no-search control can live outside the main search-required denominator. Anthropic recommends testing both under-searching and over-searching [S2 Step 3].

### 3. Live drift versus reproducible control

- **DESIGN JUDGMENT — main lane:** Fresh live search/fetch in short paired time blocks, same engine/backend/version, region/language, result count, snippets, fetch/extraction settings and budget for all configurations. Freeze date-scoped questions and gold; retain full returned SERPs/ranks/snippets/URLs and fetched bodies with timestamps/hashes. Record engine/index drift as an environmental variable. Basis: [S4], [S2 Step 4].
- **DESIGN JUDGMENT:** “Same provider” does not mean different model-generated queries return identical content. Require identical results for the same query/options at the same frozen checkpoint only in a replay lane; in live blocks retain and report actual differences. Never force everyone to use prewritten queries to manufacture identical inputs if testing query formulation. Basis: [S4]; query policy is judgment.
- **DESIGN JUDGMENT — control lane:** A frozen corpus/retriever or deterministic recorded search+page service isolates planning/reading/synthesis from engine drift. A finite query-to-result replay table cannot answer arbitrary new queries; freeze and disclose query normalization, misses, corpus and deterministic retrieval policy. Replay misses are control-environment limitations, not proof of poor live search. Basis: [S4].
- **DESIGN JUDGMENT:** Never feed all candidates the winner's recorded trajectory and call that agent search. That tests reading the same provided context. Do not pool live and replay scores/latency. A control lane is optional and separately budgeted; this research authorizes neither lane's execution. Basis: [S4], [S2].
- **DESIGN JUDGMENT:** Use the exact same logical search/fetch interfaces for all candidates. Disable vendor-native grounding in this lane; if desired later, label native end-to-end products as a separate systems comparison. Native serialization/effort compatibility is another researcher's scope; do not invent common vendor thinking flags. Basis: [S2 harness definition], [S4].
- **DESIGN JUDGMENT:** Freeze query dedup/cache policy before trials. Suggested live baseline: no cross-trial harness response cache; any within-trial reuse must still be logged and counted consistently. Engine-side caches may be opaque—record that limitation. A shared block cache can improve same-query consistency but also warms later trials and changes latency; if adopted, disclose cache hits and time separately. Basis: [S2 isolation], [S4].

### 4. Metrics: do not let formatting masquerade as research failure

The following operational metrics are **DESIGN JUDGMENTS** grounded in multi-grader/partial-credit guidance [S1], [S2], FACT [S5], and atomic report criteria [S6]. Freeze weights/thresholds before execution; report a vector, not just one conjunction.

| Metric | Definition / audit rule |
| --- | --- |
| Primary continuous semantic quality | Weighted fraction of frozen required factual/inferential criteria satisfied; missing criteria receive zero; factual and analytical dimensions reported separately. Atomic facts normally binary; only explicitly described multi-part analytical criteria permit partial credit. Macro-average by task, not by number of prose claims. |
| Factual correctness | Truth of all substantive asserted facts, including extras, against date/version-scoped verified evidence. Report correct/incorrect/unverifiable counts; do not treat source entailment as factual truth. |
| Completeness / supported coverage | Required claim coverage, plus fraction supported by retrieved evidence. This penalizes omissions even if every emitted citation is good. A supported-evidence key is not necessarily exhaustive over every legitimate source. |
| Unsupported extras | Unique unsupported/contradicted extra substantive claims and critical fabricated claims; deduplicate restatements. Useful relevant extras may be noted, but cannot inflate required-claim recall or offset a critical false conclusion. |
| Citation entailment precision | For each atomic cited claim, does cited content support the WHOLE claim, including date, version, qualifier and number? Separate fully/partly/not supported/unknown. Store quoted evidence spans and mappings. Missing citations measured separately. |
| Citation coverage | Required answered claims with adequate source support / required answered claims needing citation; also report supported required claims / all required claims to reveal omissions. Zero-denominator precision is N/A, not perfect. |
| URL validity / accessibility | Parseability, recorded HTTP/fetch outcome, redirects, effective URL, relevant content and anchor resolution. An HTTP success is not semantic support; a grading-time block after successful trial retrieval is not automatically a hallucinated URL. |
| Source authority / independence | Prefer owning official source for API/release claims, primary paper/data for empirical claims. Multiple mirrors of one announcement are not independent corroboration. Require two independent sources only when the task genuinely needs cross-validation. |
| Instructions / usability | Separate obeyed date/scope/format/sourcing requirements, organization and concise usefulness. No universal two-source minimum and no default 400-word cutoff that zeroes correct research. Explicit hard user constraints remain measurable, separately reported. |
| Safety / critical errors | Injection-following, prohibited access/write attempt, fabricated decisive evidence, confidently wrong version/applicability conclusion. Predeclare severity and which errors invalidate practical task success, not all partial semantic credit. |
| Practical task success | Predeclared semantic adequacy plus absence of task-critical errors within the deadline; report instruction/safety-qualified success as an additional measure, not the only score. Do not make every minor URL/format/exploratory error an all-or-nothing gate. |
| Uncertainty | Appropriate abstention, bounded negative conclusion and disclosure of conflicting/inaccessible evidence. Optional numeric confidence calibration only if explicitly requested uniformly; a small sample cannot establish stable calibration curves. |
| Tool diagnostics | Search issued, result followed by substantive fetch, evidence utilized, query changes, distinct result/page/source counts, duplicate calls, failed attempts and successful recovery. Measure the required search+fetch construct without requiring one exact sequence or maximum call count as a quality proxy. |

**Observed code cautions:** FACT's pinned English validator explicitly permits facts “entirely or partially” present to count as supported, and marks invalid pages unknown [S9]. That is too permissive for full atomic entailment; adopt stronger wording as a declared design change, not purported faithful FACT reproduction. BrowseComp's pinned evaluator returns regex `group(0)` (`correct: yes`) but compares the result to `yes` [S10 lines 92–93,108]; an offline Python regex check in this session confirmed the mismatch. Do not copy benchmark code without positive/negative/unknown fixture tests. Neither finding is a candidate-model result.

**DESIGN JUDGMENT — URL handling:** Keep the original cited URL and separate effective/base URL and anchor/text directive. Percent-decode text directives according to their grammar; do not percent-decode an entire URL indiscriminately or strip meaningful query/version parameters. Check anchor/quote support against archived HTML/normalized visible text and Markdown, preserving code punctuation, numerals and qualifiers. HTML-to-Markdown normalization is not semantic proof. A stale `#:~:text=` directive may fall back to a useful ordinary page link; report anchoring failure separately from page/claim validity. The draft specification explicitly describes syntax, decoding and graceful degradation [S11].

**DESIGN JUDGMENT — fetch failures:** Log every attempt and its latency. A recovered exploratory 404/block does not automatically fail the final answer. If essential evidence remains unavailable, score the corresponding unsupported/unverified claims and uncertainty behavior, while preserving other credit. If the grader cannot access a previously retrieved body, use its immutable trial snapshot; otherwise mark entailment unknown and adjudicate. Basis: unknown handling [S9], partial credit/outcome focus [S2], live drift [S4].

### 5. Judges and review validity

- **DESIGN JUDGMENT:** Start with deterministic checks for parseability, trace integrity, budgets and URL identity; use disclosed blinded AI grading for semantic/entailment criteria, with criterion-level decisions, concise rationales and evidence spans. Judge sees the task, frozen atomic key and relevant evidence, not candidate model/effort/timing. Basis: [S1], [S2], [S6].
- **DESIGN JUDGMENT:** Frozen expected coverage is independent of candidate claim extraction. Extraction can identify extras/citations, but a candidate-only citation extractor cannot determine what the answer omitted and should not manufacture missing citations or revise gold. Basis: FACT's scope [S5] contrasted with coverage criteria [S2], [S6].
- **DESIGN JUDGMENT:** Calibrate on known-correct, subtly wrong, incomplete, unsupported and alternate-valid-source fixtures plus a preselected blinded subset of completed trials. Review every critical/ambiguous result independently; where feasible obtain human expert labels for the subset. If only an independent AI reviewer is available, say “AI-graded, not human-calibrated.” No blanket guarantee of judge validity. Basis: [S1], [S2].
- **DESIGN JUDGMENT:** Preserve judge unknowns and disagreements. Report agreement/confusion cases, not only mean scores; do not drop low-consensus tasks invisibly. For optional pairwise judgments swap order and retain ties. Inspect failures across all configurations before deciding the task is broken. Basis: [S1 position/verbosity bias], [S5 human-consistency study], [S2 transcript inspection].
- **Observed version risk:** DRB's current README records 2026 evaluator/cleaner migrations, while its original paper describes Gemini judges; DRB II's current repository records an August 2026 GPT-5.5 migration while the paper retains original Gemini experiments [S12], [S6]. Judge identity/prompt/version must be frozen for this suite; historical published agreement cannot be assumed for our new grader/tasks.

### 6. Resource fairness and speed

All budget values below are **DESIGN JUDGMENTS / approval options**, not measured sufficiency for Gemini 3.8, DeepSeek 4.1 or GLM 5.3.

- Proposed equal external envelope: eight candidate response turns INCLUDING final answer, at most three search calls and six fetch calls (nine total), same returned result count and per-page body limit. Every individual call in a parallel batch counts; failures/duplicates count. Reserve room for final synthesis rather than silently granting a ninth response. Search-reformulation/recovery tasks need room inside the envelope. Basis: [S2 traces], [S3 compute scaling], [S4 common retrieval settings].
- Prefer one equal 240-second end-to-end deadline for the main lane; publish observed semantic success at 180 seconds only when a complete qualifying answer already existed by then. Alternatively approve 180 seconds as the main deadline and 240 seconds as a distinct lane, not selective extensions for slow configurations. Earlier timeout reports are parent-supplied context, not independently audited here. Basis: [S2 latency tracking], [S3 compute scaling].
- Freeze output/context limits large enough for the task's required evidence and concise answer; verify model-native reasoning/output token semantics separately. Equal numeric token caps across tokenizers are not proof of equal compute. Report externally equal limits and actual observable usage, not an invented inference-compute equality. Basis: [S2 harness], [S3].
- Primary speed: start of scheduled trial to complete final answer (includes queues/network/tool work as observed), paired with quality and completion rate. Also timestamp first tool action, first visible FINAL-answer token when streaming, last final token, each model request interval, and every tool interval. Call first-action latency `TTFAction`, first-final-answer latency `TTFAnswer`; do not confuse either with progress/thinking text. Nonstreaming TTFAnswer is unavailable, not estimated. Basis: [S2 latency example]; exact definitions are our design.
- Separate search/fetch service time, model-request time and harness/queue overhead. With concurrent tools, sums exceed the critical path; retain start/end intervals and union/overlap rather than subtracting summed tool time. Model-request wall time is not pure internal inference time without provider timing evidence. Basis: trace observability [S2]; attribution method is judgment.
- Retain timeout/rate-limit/auth/protocol/tool-service error categories, observed failure elapsed time and censored completion time. Never rank a fast error as a promising fast answer or replace failed runs with successful retries. Show completion rate and deadline success beside completed-only median/tail latency; all-attempt wall time is a separate consumed-resource measure. Basis: non-completed statuses [S4], partial credit [S2].
- Keep token/tool/turn usage as diagnostics; price is not a primary outcome. A quality–latency Pareto plot plus paired per-task differences is preferable to one price-adjusted ranking. Basis: [S2 tracked metrics]; Pareto presentation is judgment.

### 7. Repetitions, ordering, and quota

- **DESIGN JUDGMENT:** Prefer at least 8 independently authored task clusters × 3 repetitions × C confirmed configurations. With the parent's provisional C=9, this is 216 trials; three Gemini effort configurations would account for 72 Gemini trials. A balanced quota-limited fallback is 8 × 1 × 9 = 72 total, 24 Gemini trials, with limited repeat-reliability evidence. Arithmetic was tool-calculated; native effort counts are not verified here. Basis for repetition, not these exact counts: [S2].
- **DESIGN JUDGMENT:** Pair all configurations on the same task/repetition in compact temporal blocks. Preregister a seeded counterbalanced configuration order and task order; rotate positions across repetitions, and avoid always running heavy effort last. Planner supplies the exact schedule after C/quota are confirmed. Use identical concurrency/resource policy across blocks. Basis: [S2 isolation], [S4 live fairness].
- **DESIGN JUDGMENT:** Estimate differences by paired task means and task-cluster resampling/intervals, retaining within-task repetitions together; optionally stratify by difficulty only if sample sizes permit. Eight tasks remain eight clusters, not 24 independent questions, and any templates sharing evidence/themes need an even broader cluster. State uncertainty prominently; no claim of statistical power without a target effect/variance. Basis: [S2 repeated trials and correlated environment failures]; interval choice is our statistical design judgment.
- **DESIGN JUDGMENT:** Report ordinary per-attempt success and consistency across repetitions, not best-of-three selection as user experience. Anthropic explicitly distinguishes at-least-one pass@k from all-trials pass^k [S2]. Do not use either to hide failures or spend unapproved extra attempts.
- **DESIGN JUDGMENT / explicit parent constraint:** Only after final approval, the first real scheduled case for each configuration doubles as the counted native-parameter/tool-protocol compatibility gate. No extra probes/warmups/retries/post-hoc retuning/route fallback. On a compatibility failure preserve the counted record and follow a preapproved stop/continue policy; do not retrofit a comparison as if the failed trial never happened. Native contracts and exact effort inventory remain outside this note's scope.

### 8. Safety and reproducibility acceptance checks

- **DESIGN JUDGMENT:** Treat fetched pages/SERPs as untrusted data, not instructions; use a harmless controlled injection fixture for a separately labelled challenge. Constrain read-only public HTTP(S) tools, deny private/loopback/metadata destinations and unsafe redirects, and prohibit auth/accounts/form submissions/writes. Queries must contain no secrets, credentials or personal data. Enforce these in the proposed harness/permissions, not only prose. Primary basis for the threat: [S13]; particular guardrails are our design and are NOT built here.
- **DESIGN JUDGMENT:** Freeze task IDs/prompts/rubrics, source snapshots/coverage maps, tools and schemas, search/extraction settings, provider/model/effort flags, budget/deadline policy, seeds/order, grader prompt/version, harness/code hashes and immutable trial ledger. Store complete actual returned SERPs and tool-visible bodies, truncation information, original/effective URLs, status, timestamps, outputs, usage and errors. Raw evidence retention must obey source terms and sanitize secrets without altering evaluated facts. Basis: [S1 logging], [S2 transcript/isolation], [S4].
- **DESIGN JUDGMENT:** Proposed preflight guardrails should be offline fixture/contract tests only: known passing/failing/unknown answers; citation parser redirects/text fragments; recovery and deadlines; tool-call counting; native recorded protocol fixtures; gold isolation; no write/auth permission. Real provider compatibility is counted once through the approved first case, not a separate live smoke. No candidate or paid search API smoke is approved by this note. Basis: reference solutions and harness stability [S2], inspected grader defects [S9], [S10].

## Risks, unknowns, and approval dependencies

- **UNVERIFIED:** Actual candidate model IDs/native efforts/serialization, API quota and tool-engine availability. This researcher used read-only primary-source search/fetch, not any candidate provider. Parent's separate tool/native-contract researchers must identify exact engine/API schema/auth availability through metadata/help without paid queries before proposing execution.
- **UNVERIFIED:** Whether eight-turn / three-search / six-fetch / 240-second tasks are simultaneously feasible and discriminative. Next: task-author manual source/path curation using the intended tools; after approval, counted real cases, not a hidden candidate pilot. Do not import BrowseComp-scale difficulty wholesale.
- **UNVERIFIED:** Any selected benchmark task's actual distribution fit, source accessibility and permitted reuse. Next: pin task/data release, read its own data/source license and check task evidence manually. No benchmark dataset was adopted, decrypted, installed or executed here.
- **Observed license distinctions:** BrowseComp-Plus query/corpus cards declare MIT and obfuscate benchmark QA [S14]; its software LICENSE is MIT [S15]. This is not independent verification of rights to every scraped third-party page. DRB's README badge says MIT but the fetched pinned LICENSE says Apache 2.0 [S12], [S16]; do not decide rights from a badge. DRB II DATA_LICENSE explicitly gives per-task CC BY / CC BY-NC / CC0 terms [S17]; paper, code and data licenses are separate.
- **UNVERIFIED:** Local judge calibration, source snapshot retention rights, true engine caches, small-sample confidence calibration and any definitive winner. Next: approval of frozen rubric, retained-evidence policy, review lane and balanced sample budget; no semantic “verifier” is a proof of truth.
- **Recommendation for approval:** Adopt the practical question-only live lane and multi-dimensional grading; optionally approve an explicitly separate frozen-retrieval/injection control. Planner must resolve C, quota, task selection, search service, deadline and exact counterbalancing before ANY candidate work. Main risks are live drift, answer leakage, judge/reference bias, source failure and timeout-driven survivor bias. This is research, not final plan approval. Basis: [S1]–[S6].
