## pytest-dev/pytest — #14773

**Pinning and sources.** Base `ced9022c0ca87ae2a0a604c68d2e1c462f8a5c6f`, head `4d81b842a5a2af9d3160e7b3895b7d78604d19bb`: [commit with parent and diff](https://github.com/pytest-dev/pytest/commit/4d81b842a5a2af9d3160e7b3895b7d78604d19bb), [comparison](https://github.com/pytest-dev/pytest/compare/ced9022c0ca87ae2a0a604c68d2e1c462f8a5c6f...4d81b842a5a2af9d3160e7b3895b7d78604d19bb), [CONTRIBUTING.rst at head](https://github.com/pytest-dev/pytest/blob/4d81b842a5a2af9d3160e7b3895b7d78604d19bb/CONTRIBUTING.rst#L283-L305). The issue reports `parser.addoption("shuffle")` causing `AttributeError` in pytest 8.4.2 with Python 3.13.7; the PR says it avoids a second `AttributeError` through a default value in `Argument.dest` ([issue](https://github.com/pytest-dev/pytest/issues/13817), [PR](https://github.com/pytest-dev/pytest/pull/14773)).

- **Verification of *Spec*.** The only production change is `getattr(self._action, "dest", "<missing>")` in [`src/_pytest/config/argparsing.py:303–305`](https://github.com/pytest-dev/pytest/blob/4d81b842a5a2af9d3160e7b3895b7d78604d19bb/src/_pytest/config/argparsing.py#L303-L305). At the same head, [`_addoption_inner()` obtains the `Action` from `add_argument()` before creating `Argument(action)`](https://github.com/pytest-dev/pytest/blob/4d81b842a5a2af9d3160e7b3895b7d78604d19bb/src/_pytest/config/argparsing.py#L383-L397): if the construction of the action fails, there is no partial action encapsulated on this route. The method `_set_opt_strings` mentioned in the [added test](https://github.com/pytest-dev/pytest/blob/4d81b842a5a2af9d3160e7b3895b7d78604d19bb/testing/test_config.py#L2490-L2502) no longer exists in that file. In the pinned checkout, `Parser(_ispytest=True).addoption("shuffle")` **returned without error**, and `pytest --help` with the issue's `conftest.py` exited with code 0, without `AttributeError`. This does not confirm that accepting `shuffle` as a positional option is desirable; the acceptance, however, already followed from the flow unchanged by the PR and the issue does not define this requirement as an acceptance criterion. **There is no safe *Spec* target** of "the `AttributeError` keeps happening".
- ***Standards* rule and limit.** The guide says tests are *frequently* done as black-box through the `pytester` fixture, [without making it mandatory](https://github.com/pytest-dev/pytest/blob/4d81b842a5a2af9d3160e7b3895b7d78604d19bb/CONTRIBUTING.rst#L428-L465). The new test builds a `BrokenAction` without `dest` and uses `# type: ignore`, instead of registering the option given in the issue; it passed (`1 passed`), but does not prove the alleged route ([test at head](https://github.com/pytest-dev/pytest/blob/4d81b842a5a2af9d3160e7b3895b7d78604d19bb/testing/test_config.py#L2490-L2502)). This is a risk to test quality, not an unambiguous violation of the black-box guidance. The required changelog was included ([file](https://github.com/pytest-dev/pytest/blob/4d81b842a5a2af9d3160e7b3895b7d78604d19bb/changelog/14773.bugfix.rst#L1)); the lack of an entry in `AUTHORS` depends on the exception for trivial changes ([rule](https://github.com/pytest-dev/pytest/blob/4d81b842a5a2af9d3160e7b3895b7d78604d19bb/CONTRIBUTING.rst#L299-L305)) and should not become a target without that decision.
- **Limit of the reproduction.** The host offers Python 3.14.6, not the reported 3.13.7. I used an isolated installation of the code at head, with minimal dependencies; since the GitHub tarball does not contain `.git`, a version had to be supplied only for the installation through `setuptools-scm`. I did not reproduce the historical error of pytest 8.4.2 nor prove the absence of other paths with a custom `Action`. The conclusion is restricted to the original example at head and to the diff examined.

## axios/axios — #10852

**Pinning and sources.** Base `05436fd562027a9d10531d58d13dd33d7f222c0c`, head `7b51e6d70b383f308cb97dfb1abc59daae187e61`: [commit with parent and diff](https://github.com/axios/axios/commit/7b51e6d70b383f308cb97dfb1abc59daae187e61), [comparison](https://github.com/axios/axios/compare/05436fd562027a9d10531d58d13dd33d7f222c0c...7b51e6d70b383f308cb97dfb1abc59daae187e61). The [issue](https://github.com/axios/axios/issues/6546) provides `axios.get(new URL(...), {params: {test: "Hi"}})` in the browser and asks that the client accept the object as it accepts its textual representation; the [PR](https://github.com/axios/axios/pull/10852) states it offers support for `URL` objects in the Axios methods.

- **Confirmed *Spec* target, with a scope caveat.** The added conversion occurs only in [`buildURL.js:36–39`](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/lib/helpers/buildURL.js#L31-L39). With `baseURL` configured, the flow first reaches [`resolveConfig()` → `buildFullPath()`](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/lib/helpers/resolveConfig.js#L51-L61); [`isAbsoluteURL()` considers any non-absolute object](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/lib/helpers/isAbsoluteURL.js#L10-L18), and [`combineURLs()` calls `.replace()` on the object](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/lib/helpers/combineURLs.js#L11-L14). On Node 22.23.2, `axios.get(new URL('https://example.com/foo'), {baseURL:'https://api.example/', params:{test:'Hi'}, adapter:'fetch'})` rejected with `TypeError: relativeURL.replace is not a function`; `adapter:'http'` failed the same way, before any network request. The `URL` object did not reach the modified line. The **strictly literal** example in the issue does not set `baseURL`: if the yardstick limits the requirement to the call without `baseURL`, do not turn this variant into a failure of the issue. The target is solid when the frozen goal is the promised support for `URL` in the methods, including with the common `baseURL` configuration.
- **Confirmed *Standards* target.** [`CONTRIBUTING.md:13–19` at head](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/CONTRIBUTING.md#L13-L19) orders tests to be updated according to the code and says PRs with failing tests will not be accepted. [`buildURL()` returns before the conversion if `params` is null](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/lib/helpers/buildURL.js#L31-L39), whereas the [new test requires a string](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/tests/unit/helpers/buildURL.test.js#L104-L112). I ran `npm run test:vitest:unit -- tests/unit/helpers/buildURL.test.js` at head: **21 passed, 1 failed**, precisely at `:111` (`URL {}` received, string expected). This target locates a changed assertion, a current rule and a current failure; it does not depend on deducing CI failure or on demanding absent tests. The documentation rule is also express, but the mere absence of an edit in `docs/` is mainly a process pending item, not a strong additional target by itself.
- **Other defects and care in assembly.** Without parameters, `buildURL(url, null)` still returns an object, and `axios.getUri({url})` returned the same object although it declares a `string` return ([code](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/lib/core/Axios.js#L233-L237), [types](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/index.d.ts#L603-L625)); this **does not prove** that every request without parameters fails. The public types still require `url: string` in the methods: `tsc` rejected `axios.get(new URL('https://example.com'))` with `TS2345` ([declarations](https://github.com/axios/axios/blob/7b51e6d70b383f308cb97dfb1abc59daae187e61/index.d.ts#L609-L628)). These are additional observations to be adjudicated regarding the issue's reach, not targets to hide or add after the first response. If this case is used, explicitly freeze which scenarios are part of the answer key and deliver non-editorialized context on `baseURL`, tests and types; do not give the model these reproductions.
- **Limit of the reproduction.** I installed dependencies in a temporary copy of the commit tarball and ran the repository's unit suite on Node, without a browser. The error with `adapter:'fetch'` and `adapter:'http'` occurs before the network and is independent of the server; I did not run the original example in a browser nor the distribution build.

## spf13/cobra — #1664

**Pinning and sources.** Base `9d15fe657a500065fb343f8a9d1474582147f828`, head `6cf30ea48100c84c2f6f269d731fcff505cf4000`: [commit with parent and diff](https://github.com/spf13/cobra/commit/6cf30ea48100c84c2f6f269d731fcff505cf4000), [comparison](https://github.com/spf13/cobra/compare/9d15fe657a500065fb343f8a9d1474582147f828...6cf30ea48100c84c2f6f269d731fcff505cf4000). The [issue](https://github.com/spf13/cobra/issues/1663) wants to omit hidden flags from the generated documentation, including deprecated ones that remain hidden; it notes that a flag made visible after deprecation may appear.

- **Fulfilled part of *Spec*.** The only four lines added make [`genFlagResult()` skip `flag.Hidden`](https://github.com/spf13/cobra/blob/6cf30ea48100c84c2f6f269d731fcff505cf4000/doc/yaml_docs.go#L148-L155). The function feeds **both** [`Options` and `InheritedOptions`](https://github.com/spf13/cobra/blob/6cf30ea48100c84c2f6f269d731fcff505cf4000/doc/yaml_docs.go#L110-L117). The man page generator [already ignores `Hidden`](https://github.com/spf13/cobra/blob/6cf30ea48100c84c2f6f269d731fcff505cf4000/doc/man_docs.go#L158-L162), and the Markdown one uses `HasAvailableFlags()` and `PrintDefaults()` ([code](https://github.com/spf13/cobra/blob/6cf30ea48100c84c2f6f269d731fcff505cf4000/doc/md_docs.go#L29-L45)). With visible and hidden flags, local and inherited, I generated YAML, Markdown and man page at that head: all three included the visible ones and omitted the hidden ones; `go test ./doc` passed. Therefore, it does not support simply claiming that the fix "forgot Markdown/man".
- ***Spec* exception still broken, outside the diff.** [Issue #1663](https://github.com/spf13/cobra/issues/1663) notes that a flag explicitly made visible after being deprecated may appear in the documentation. The pinned dependency is [`pflag v1.0.5`](https://github.com/spf13/cobra/blob/6cf30ea48100c84c2f6f269d731fcff505cf4000/go.mod#L5-L9), whose [`MarkDeprecated()` also sets `Hidden=true`](https://github.com/spf13/pflag/blob/v1.0.5/flag.go#L404-L439); therefore, it is possible to make it visible later through `Lookup(name).Hidden = false`. I did this with a local flag `restored-deprecated`: the generated YAML and Markdown included it, but the man page omitted it because [`manPrintFlags()` filters `Deprecated` even when `Hidden=false`](https://github.com/spf13/cobra/blob/6cf30ea48100c84c2f6f269d731fcff505cf4000/doc/man_docs.go#L158-L162). This is a reproducible failure **if the issue's caveat applies to all outputs**. However, the man page filter pre-existed in the base and the PR changes only YAML: it is a target of a requirement unmet by omission, without a changed location in the causing code. Do not present it as a regression introduced by the four lines.
- **Rule of *Standards* and limit.** [`CONTRIBUTING.md:29–36`](https://github.com/spf13/cobra/blob/6cf30ea48100c84c2f6f269d731fcff505cf4000/CONTRIBUTING.md#L29-L36) asks for adequate tests for code contributions. The diff adds no tests and the [existing YAML tests](https://github.com/spf13/cobra/blob/6cf30ea48100c84c2f6f269d731fcff505cf4000/doc/yaml_docs_test.go#L13-L68) check visible, not hidden, flags. This leaves the change without protection against regressions, but does not produce a failing test at head; it would be a target of **process/coverage only**. The short diff and the *Spec* failure in unchanged code make the *Spec*/*Standards* pair less suitable than the axios one.
- **Limit of the reproduction.** I used Go 1.27.1 on macOS and the dependencies from `go.mod` ([file at head](https://github.com/spf13/cobra/blob/6cf30ea48100c84c2f6f269d731fcff505cf4000/go.mod#L1-L10)); I did not run `go test ./...` nor examine all possible states of `pflag.Flag`. The proofs cover the three generators, local and inherited flags, and the exception of a deprecated flag made visible; they do not cover other imaginable formats.

**Research decision:** keep axios under the scope caveat above; look for substitutes for pytest and, preferably, Cobra before freezing the three cases. To keep Cobra, it would be necessary to expressly assume the man page exception as a requirement of the issue, accept a *Standards* target of coverage only, and include unchanged context from that generator in the review material. Review comments, test omission and lack of a changelog should not be converted into a positive answer key for convenience.

### rust-lang/rust — #161834

**Pinning, origin and diff.** Base `ac7f9ec7da74d37fd28667c86bf117a39ba5b02a` (parent of the PR's first commit), head `152379d7dd1615ef8b951ee7a579c5b3706130b9` ([pinned comparison](https://github.com/rust-lang/rust/compare/ac7f9ec7da74d37fd28667c86bf117a39ba5b02a...152379d7dd1615ef8b951ee7a579c5b3706130b9); [first commit and parent](https://github.com/rust-lang/rust/commit/772b5ecfe59fcfc9052a3f5eefa5d404b8b18a43); [second commit](https://github.com/rust-lang/rust/commit/152379d7dd1615ef8b951ee7a579c5b3706130b9)). [Issue #161735](https://github.com/rust-lang/rust/issues/161735) asks that the search `Vec<T> -> Result<Box<_>, _>` find the implementation of `TryFrom<Vec<T>> for Box<[T; N]>`; the explicit query with `[T; N]` produces another error, a syntax one. The [PR](https://github.com/rust-lang/rust/pull/161834) promises both improvements, although it calls its new test a *placeholder*.

- **Target *Spec*: the wildcard search in the issue was not fixed.** The only executable change in [`src/librustdoc/html/static/js/search.js:318`](https://github.com/rust-lang/rust/blob/152379d7dd1615ef8b951ee7a579c5b3706130b9/src/librustdoc/html/static/js/search.js#L312-L320) starts recognizing `;` as a separator. The main query of the issue **does not contain `;`**. I compared the complete files of base and head: besides this line, the only change in the researched indexing path is a [comment in `search_index.rs:2180`](https://github.com/rust-lang/rust/blob/152379d7dd1615ef8b951ee7a579c5b3706130b9/src/librustdoc/html/render/search_index.rs#L2175-L2188), with no change in the indexed type. I ran `DocSearch.parseQuery()` of the pinned JavaScript, at both commits: `Vec<T> -> Result<Box<_>, _>` continued without error and with one input element and one return element in both; `Vec<T> -> Result<Box<[T; N]>, _>` changed from `Unexpected ; after T` to *no error*. Therefore, the PR fixes **the second complaint**, but leaves unchanged the parse and the indexing relevant to **the main query that was not finding results**. The conclusion about the result of that search combines the issue's report with the equivalence of the executable paths; I did not run a complete search against a `std` index regenerated at head, nor do I attribute a numeric result to that index.
- **Target *Standards*: new file violates the format required by the `rustdoc-js` test executor.** The [testing guide](https://github.com/rust-lang/rust/blob/152379d7dd1615ef8b951ee7a579c5b3706130b9/src/doc/rustc-dev-guide/src/tests/compiletest.md) identifies `rustdoc-js` as the suite for the search engine and index. The [executor at head, `tester.js:363–405`](https://github.com/rust-lang/rust/blob/152379d7dd1615ef8b951ee7a579c5b3706130b9/src/tools/rustdoc-js/tester.js#L363-L405), itself establishes the verifiable rule: **"At least `PARSED` or `EXPECTED` is needed!"**; only those declarations trigger the parse or search checks. The [added file](https://github.com/rust-lang/rust/blob/152379d7dd1615ef8b951ee7a579c5b3706130b9/tests/rustdoc-js/search-issue-161735.js#L1-L12) contains `describe`/`it`, comments and a `query` variable, without `PARSED`, `EXPECTED` or an assertion that queries the search. When calling `runChecks()` of this executor directly on the file at head, I got `FAILED`, the message above, return `1` and **zero calls** to the parse/search functions. This is a violation of the suite's contract in the added line itself, not just a preference for more tests. I do not claim, without running the *bootstrap*, that CI discovers this `.js` alone without a corresponding `.rs`; in either case it is not a valid regression test for the two promises. The [general guidance on regression tests](https://github.com/rust-lang/rust/blob/152379d7dd1615ef8b951ee7a579c5b3706130b9/src/doc/rustc-dev-guide/src/tests/adding.md#L1-L6) reinforces the purpose, but refers literally to compiler fixes; the **contract applicable here** is that of `tester.js`.

Do not deliver the result of the experiments nor a reproduction test that reveals the findings. The parser reproduction used Node 22 in an isolated module, without `./x test` nor a compiled documentation index; the proof of non-change of the wildcard query is from flow/diff, not a measurement of the public page at that commit.

### prettier/prettier — #19906

**Pinning, origin and diff.** Base `9c7728d3b495e4c40a75d0c1e0d8df2ee68bc6ab`, head `8f32b7b8f9e97cfc3989732457951d5f4fec6bc5` ([pinned comparison](https://github.com/prettier/prettier/compare/9c7728d3b495e4c40a75d0c1e0d8df2ee68bc6ab...8f32b7b8f9e97cfc3989732457951d5f4fec6bc5)). The base is the **second parent of the merge** that closes the head, not the first: `git diff` between these commits contains exactly the three files of the PR (`changelog_unreleased/javascript/19906.md`, `src/language-js/print/binaryish.js` and `src/main/multiparser.js`; 239 additions, 164 removals). [Issue #16531](https://github.com/prettier/prettier/issues/16531) provides a reproduction with `prettier.format(..., { filepath: 'test.ts' })` over a class with hundreds of concatenated literals. The [PR](https://github.com/prettier/prettier/pull/19906) calls itself a solution for the issue and states it replaces with iteration two recursions, in `binaryish.js` and `multiparser.js`; it expressly delimits as out of scope a later failure in the third-party parser `@babel/parser`.

- **Main *Spec* target: the original TypeScript reproduction still ends in `RangeError`.** I downloaded the pinned base and head, installed the dependencies with `yarn install --immutable` and ran the input copied from the issue (825 literals, 824 `+` operators, `filepath: 'test.ts'`). I adjusted **only the import of the small reproduction script** from `import prettier from 'prettier'` to `import * as prettier from 'prettier'`, because the current module does not provide a *default* export; content to format and file option remained the same. Base and head ended with `RangeError: Maximum call stack size exceeded` in the AST conversion of `@typescript-eslint/typescript-estree` (`getModifiers.js`/`convert.js`). The equivalent call through the CLI, with `--parser typescript`, also exited with code `2` at head. The [TypeScript parser](https://github.com/prettier/prettier/blob/8f32b7b8f9e97cfc3989732457951d5f4fec6bc5/src/language-js/parse/typescript.js#L1-L15) runs before the two modified traversals; thus, these cannot cure the **literal** failure of the issue. This is an unmet requirement, not a regression introduced in the PR. **Essential caveat:** the author acknowledged a third-party parser limit and declared it outside their scope; this finding holds if the yardstick takes the issue associated by `Fixes #16531` as the goal, according to the [approved design](../docs/superpowers/specs/2026-09-26-code-review-eval-v2-design.md#prompts-em-inglês). If the review is deliberately restricted to the two recursions pointed out by the author, do not call the external failure a bug *in those* lines.
- **Independent limit, in own code, of the promise about depth.** So as not to depend only on the external parser, I generated `const x = ` followed by `5.500` literals `"a"` joined by `+` and ran the head with `node bin/prettier.cjs --parser meriyah`. It exited with code `2` and `RangeError`, now in [`postprocess/index.js:95–97`](https://github.com/prettier/prettier/blob/8f32b7b8f9e97cfc3989732457951d5f4fec6bc5/src/language-js/parse/postprocess/index.js#L93-L99) → [`visit-node.js:20–31`](https://github.com/prettier/prettier/blob/8f32b7b8f9e97cfc3989732457951d5f4fec6bc5/src/language-js/parse/postprocess/visit-node.js#L18-L32), which still traverses the tree recursively **before** the new loops. At `4.000` literals, the base failed and the head passed: there is real improvement, but the remaining limit is in Prettier itself. The PR claims to process approximately `5.000–7.500` elements before a *separate* limit in `@babel/parser`; this claim does not hold for the `meriyah` parser with `5.500` on this installation. Do not extrapolate a universal limit: the depth at which the Node stack overflows varies with runtime and environment. This is an alternative or complementary scope target, not proof that **all** deep inputs fail.
- **Substantive *Standards* target: modified code does not follow the formatter required by the repository itself.** The [contribution guide at head, `CONTRIBUTING.md:93`](https://github.com/prettier/prettier/blob/8f32b7b8f9e97cfc3989732457951d5f4fec6bc5/CONTRIBUTING.md#L89-L95), says literally: **"The project uses ESLint for linting and Prettier for formatting. If your editor isn't set up to work with them, you can lint and format all files from the command line using `yarn fix`."** I ran the formatter of the **pinned checkout itself**, `node bin/prettier.cjs --check src/main/multiparser.js src/language-js/print/binaryish.js`: base, code `0`, both conforming; head, code `1`, **both** files flagged.
