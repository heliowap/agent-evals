The two supplied sources are fetched. Now I'll check the version-matched CLI reference, since the permissions page references the flag definitions there (for `--permission`, `--allow-worker`, `--env-file`).

## Decision: not certifiable as tenant isolation; redesign required

**1. The core premise is wrong.** The version-matched Permission Model docs state the feature "does not protect against malicious code… Malicious code can bypass the permission model and execute arbitrary code without the restrictions imposed" ([permissions.html#permission-model](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model)). The v24.21.0 Security Policy says Node.js trusts "the code it is asked to run" (not even third-party modules), and lists "Exposing Application-Level APIs to Untrusted Users (CWE-653)" as an application-responsibility non-vulnerability ([SECURITY.md](https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md)). Recommendation: put each tenant's code in OS-level isolation (separate OS users/processes, per the docs' own mitigation guidance [permissions.html#process_debugprocess…](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#process_debugprocess-and-cross-process-inspector-activation)); use `--permission` only as defense-in-depth for your trusted launcher.

**2. The read grant is broader than assumed.** "After passing a wildcard character (\*) all subsequent characters will be ignored," so `--allow-fs-read=/srv/jobs/*.js` behaves as `/srv/jobs/*` ([permissions.html#file-system-permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#file-system-permissions)). Entrypoints and `--require` preload modules get implicit read ([cli.html#--allow-fs-read](https://nodejs.org/download/release/v24.21.0/docs/api/cli.html#--allow-fs-read)). Use dedicated per-tenant directories with explicit grants.

**3. Symlinks violate a documented precondition.** Relative symlinks "may allow access to arbitrary files and directories"; you "must ensure that no paths to which access has been granted contain relative symbolic links" ([permissions.html#limitations-and-known-issues](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#limitations-and-known-issues)). Resolve/copy job trees to realpath-clean directories before granting.

**4. `--env-file` is outside the model by design.** Flags like `--env-file` read files "before environment initialization… not subject to the rules of the Permission Model" ([permissions.html#permission-model-constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)); it also parses and applies `NODE_OPTIONS`, which may legally contain `--permission`/`--allow-fs-read` ([cli.html#--env-filefile](https://nodejs.org/download/release/v24.21.0/docs/api/cli.html#--env-filefile), [cli.html#node_optionsoptions](https://nodejs.org/download/release/v24.21.0/docs/api/cli.html#node_optionsoptions)). Its exclusion from the read list is irrelevant; no scope protects `process.env`, and workers copy it ([worker_threads.html#class-worker](https://nodejs.org/download/release/v24.21.0/docs/api/worker_threads.html#class-worker)). Treat env files as operator-trusted, secrets included.

**5. The pre-opened fd is an explicit bypass.** "Using existing file descriptors via the node:fs module bypasses the Permission Model," and `permission.drop()` never revokes already-open resources ([permissions.html#permission-model-constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)). Acceptable as a deliberate capability handoff; not an isolation mechanism.

**6. Worker inheritance is UNVERIFIED.** The API docs state "The model does not inherit to a worker thread" ([permissions.html#permission-model-constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)), while the same repo's Security Policy states workers "inherit the permission restrictions of their parent process" and modified `execArgv` grants nothing extra ([SECURITY.md](https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md), "Permission Model Boundaries"). These conflict; no consistent documented answer, so no silent choice. Resolve empirically on v24.21.0 and via nodejs/security-wg; meanwhile, don't expose worker-thread creation (`--allow-worker`) to job code.

**7. Audit mode denies nothing** ([permissions.html#audit-mode](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#audit-mode)); a staged audit run proves nothing about enforce mode.

**Useful for trusted application code:** audit mode + `node:permission-model:*` diagnostics channels; runtime `permission.has()`/`permission.drop()`; explicit-path grants; per-worker `resourceLimits` (JS-engine only) ([worker_threads.html#worker_threadsresourcelimits](https://nodejs.org/download/release/v24.21.0/docs/api/worker_threads.html#worker_threadsresourcelimits)). Note SQL-level file access via `node:sqlite` is not intercepted ([SECURITY.md](https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md)).

**Certification:** none possible — both sources position the model as a trusted-code seat belt.
