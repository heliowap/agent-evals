## Decision: Fix four things; do not claim exactly-once

**Authenticity evidence — signature only.** Verify the `X-Hub-Signature-256` header (HMAC-SHA256 over the raw body using the webhook secret) before processing. GitHub states the hash is "generated using your webhook's secret token and the payload contents," so you must hash the exact received bytes — parsing and re-serializing changes bytes and breaks verification. It also warns: "Never use a plain == operator"; use a constant-time comparison (`hmac.compare_digest`, `crypto.timingSafeEqual`). The GUID header is an identifier, not authentication. [validating-webhook-deliveries#validating-webhook-deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries)

**Identifier behavior — correct the wrong premise.** `X-GitHub-Delivery` is "a globally unique identifier (GUID)," but for redelivery: "If you request a redelivery, the X-GitHub-Delivery header will be the same as in the original delivery." [best-practices#use-the-x-github-delivery-header](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header). So a redelivery is **not** a new event ID — the store must dedup on the GUID and treat a redelivery as the same event, not a duplicate to process again. [webhook-events-and-payloads#delivery-headers](https://docs.github.com/en/webhooks/webhook-events-and-payloads#delivery-headers)

**Timing/retry — the ops plan is wrong.** Respond 2XX **within 10 seconds** or "GitHub terminates the connection and considers the delivery a failure." Enqueue the 25-second job and return immediately. [best-practices#respond-within-10-seconds](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds). Critically: "GitHub does **not** automatically redeliver failed deliveries"; you (or a script) must redeliver manually, and only deliveries "in the past 3 days." [redelivering-webhooks#about-redelivering-webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks)

**Minimum changes**
1. Verify signature on raw bytes before any parse.
2. Use constant-time comparison.
3. Ack 2XX <10 s; process asynchronously from a durable queue.
4. Dedup/case on `X-GitHub-Delivery`; on a known GUID, no-op success.
5. Ops: automated redelivery of deliveries within 3 days; do not assume GitHub retries.

**Exactly-once across a receiver crash: NO.** These documented mechanisms (signature, GUID, manual redelivery) show at-least-once-style delivery but give no transactional guarantee that business side effects occur exactly once if the receiver crashes mid-processing. **UNVERIFIED** — GitHub's pages state no delivery-count guarantee. Resolve via an idempotent business key + durable dedup store + transactional outbox, and check GitHub's webhook delivery-guarantee statements (not present on these pages).
