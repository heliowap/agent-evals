## Decision

Use **long-form depends_on** for the API:

```yaml
depends_on:
  db: {condition: service_healthy, restart: true}
  migrate: {condition: service_completed_successfully}
```

**Why each piece (documented facts)**

- Short syntax only guarantees *started*, not healthy — "Compose does not wait for dependency services to be 'healthy'" ([services](https://docs.docker.com/reference/compose-file/services/#long-syntax-1)); Compose "does not wait until a container is 'ready', only until it's running" ([startup order](https://docs.docker.com/compose/how-tos/startup-order/#control-startup)). So your current short-form db dependency does **not** cover health.
- `service_healthy` is the documented readiness gate, using the db `healthcheck` ([startup order](https://docs.docker.com/compose/how-tos/startup-order/#control-startup)).
- Migration: `service_completed_successfully` means "a dependency is expected to run to successful completion before starting a dependent service" ([services](https://docs.docker.com/reference/compose-file/services/#long-syntax-1)). Make the migration service exit 0; add `restart: "no"` and `depends_on: db: {condition: service_healthy}` so it doesn't run against a cold DB.

**What 2.18.0 cannot support**

- `required: false` on depends_on was **introduced in Compose 2.20.0** ([services](https://docs.docker.com/reference/compose-file/services/#long-syntax-1)). On 2.18.0 it is not available — the constant "without upgrading the plugin" premise is incorrect. Either upgrade, or gate telemetry with `profiles` ([services](https://docs.docker.com/reference/compose-file/services/#profiles)).
- `restart: true` **is** available (introduced 2.17.0). But it applies only "to an explicit restart controlled by a Compose operation, and excludes automated restart by the container runtime after the container dies" ([services](https://docs.docker.com/reference/compose-file/services/#long-syntax-1)). So `docker compose restart db` propagation is documented; runtime/`restart: always` crash-restarts are **not** propagated. That part of the proposal is UNVERIFIED as a guarantee — it is contradicted by the docs.

**Lifecycle separation**

| Event | Covered by |
|---|---|
| Container startup order | depends_on (any form) |
| Health/readiness gate | `service_healthy` |
| Migration success | `service_completed_successfully` |
| Explicit Compose restart | `restart: true` |
| Runtime crash restart | **Not covered** |

**Promise about remaining ready**

No. This configuration is startup-ordering only; nothing re-checks health after startup. To survive later DB failures, the API needs its own reconnect/retry and a healthcheck; verify recovery behaviour against Docker's Engine restart-policy semantics ([docker run --restart](https://docs.docker.com/reference/cli/docker/container/run/#restart)) — that page is the missing evidence target.
