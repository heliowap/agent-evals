## Decision: minimum changes

**1. Verify the signature, not the re-serialization.** The `X-Hub-Signature-256` digest is an HMAC-SHA256 computed with your secret over the raw payload bytes. Compute the HMAC over the original request body **before** any JSON parse/re-serialize, and confirm it starts with `sha256=`. If you re-serialize first, verification will fail (or, worse, silently verify a mutated body). GitHub also explicitly says: "Never use a plain == operator" — use constant-time comparison (e.g. `crypto.timingSafeEqual`) to mitigate timing attacks. [Validating webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries). UTF-8 handling matters for unicode payloads. [Ibid.](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#about-validating-webhook-deliveries)

**2. Respond within 10 seconds; run the 25s job asynchronously.** GitHub terminates the connection and treats the delivery as failed if no 2XX response arrives within 10 seconds; GitHub docs recommend queueing (RabbitMQ, Resque, RQ, etc.) and responding immediately. [Best practices — Respond within 10 seconds](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds) Your 25-second synchronous job is guaranteed to mark deliveries as failures.

**3. Correct the ops assumption: GitHub never auto-redelivers.** "GitHub does not automatically redeliver failed deliveries." You can only redeliver manually (web UI or REST API) and only for deliveries from the **past 3 days**; repo webhooks require admin access. [Redelivering webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks) The recovery plan therefore needs your own watchdog: list failed deliveries via the REST API and redeliver them after an outage within the 3-day window.

**4. Fix the dedup identifier.** For replay protection, GitHub says to use `X-GitHub-Delivery` "to ensure that each delivery is unique per event," and — critically — "If you request a redelivery, the X-GitHub-Delivery header will be the same as in the original delivery." [Best practices — Use the X-GitHub-Delivery header](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header) So your dedup store's "new delivery identifier on redelivery" premise is false per documentation: deduplicate on the delivery GUID, which is **stable across requested redeliveries** (and treat a GUID seen before as either a replay to drop or a legitimate recovery to process — decide both ways by your recovery goal).

## Exactly-once across a crash: **No.**
Documented mechanisms give at-least-once delivery + an authentically GitHub-originated, GUID-stable signal — i.e., the inputs you need. But exactly-once business side effects require that your dedup check and the side effect commit atomically and durably (e.g., persist the GUID in the same transaction as the business effect, then ack to GitHub). GitHub's docs document replay protection and redelivery mechanics, not transactional [UNVERIFIED beyond docs' scope]. That is your design, not GitHub's; if you cannot commit atomically, you have at-least-once + idempotency ("effectively once"), which is the documented-safe ceiling.
