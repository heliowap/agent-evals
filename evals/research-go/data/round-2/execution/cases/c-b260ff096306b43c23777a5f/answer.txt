## Decision: four minimum changes before launch

1. **Verify before parsing.** Compute `X-Hub-Signature-256` over the **raw request bytes** before any JSON parse/re-serialize; the header is the HMAC-SHA256 hex digest of the body using your secret. GitHub warns that payloads/headers must not be modified before verification ([validating-webhook-deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries), [#troubleshooting](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#troubleshooting)).
2. **Constant-time compare.** GitHub: "Never use a plain `==` operator"; use `secure_compare`, `crypto.timingSafeEqual`, or `hmac.compare_digest` ([#validating-webhook-deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries)).
3. **Ack fast, work later.** Return 2XX within 10 seconds and queue the 25-second job; beyond 10 seconds GitHub terminates the connection and records failure ([best-practices #respond-within-10-seconds](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds)).
4. **Fix dedup premise.** Redelivery keeps the same identifier: "If you request a redelivery, the X-GitHub-Delivery header will be the same as in the original delivery" ([#use-the-x-github-delivery-header](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header)). Treating redelivery as new causes duplicate processing. Use the GUID as the idempotency key for replay/duplicate protection.

## Authenticity evidence and timing

The signature over exact bytes is the authenticity/tamper evidence; HTTPS keeps SSL verification on, and a GitHub IP allowlist is optional extra blocking ([#use-a-webhook-secret](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-a-webhook-secret), [#allow-githubs-ip-addresses](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#allow-githubs-ip-addresses)). Without a secret, no signature header is sent.

**Correct the retry assumption:** "GitHub does not automatically redeliver failed deliveries"; redelivery is manual via UI/REST API and limited to deliveries from the past 3 days ([handling-failed-deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#about-webhook-delivery-failures), [redelivering-webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks)). Run a scheduled API-based redelivery script inside that window. Also note the 25 MB payload cap ([payload cap](https://docs.github.com/en/webhooks/webhook-events-and-payloads#payload-cap)).

## Exactly-once?

No. These mechanisms establish authenticity and replay/receipt dedup, not exactly-once side effects across a receiver crash (the transactional gap between committing an effect and recording the GUID is not addressed). That guarantee is UNVERIFIED — resolving it needs a GitHub statement, not generic advice. Recommendation: make the business effect idempotent and atomically commit it with the GUID dedupe record.
