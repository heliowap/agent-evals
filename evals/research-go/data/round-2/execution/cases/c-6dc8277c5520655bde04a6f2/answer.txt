## Decision: not sufficient

**Premise is wrong.** PostgreSQL's Repeatable Read (RR) does prevent phantoms — stronger than the SQL standard minimum, which permits them. But PG's RR is Snapshot Isolation; it still permits *serialization anomalies*, and the docs state that "attempts to enforce business rules by transactions at this isolation level are not likely to work correctly without careful use of explicit locks" ([transaction-iso.html#XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). Two RR workers that read the invariant then write different rows can form a read/write cycle neither detects ([applevel-consistency.html#APPLEVEL-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#APPLEVEL-CONSISTENCY)).

**Narrow changes.**
1. Run the whole read-decide-write unit at **SERIALIZABLE**, which adds nonblocking monitoring of exactly those cycles ([transaction-iso.html#XACT-SERIALIZABLE](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)).
2. Staying on RR requires explicit blocking locks (`SELECT FOR UPDATE`/`LOCK TABLE`), taken before the snapshot freezes ([applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY), [explicit-locking.html#LOCKING-ROWS](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)).
3. Classify failures by SQLSTATE, not message text ([errcodes-appendix.html#ERRCODES-TABLE](https://www.postgresql.org/docs/18/errcodes-appendix.html#ERRCODES-TABLE)).

**Ownership and retry unit.** The application owns retrying: PostgreSQL "does not offer an automatic retry facility," and the docs tell you to "retry the complete transaction, including all logic that decides which SQL to issue and/or which values to use" ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Statement-level replay cannot work — the prior reads and chosen values no longer exist; RR docs say abort and retry from the beginning ([transaction-iso.html#XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). Note retry lives outside the transaction; PL/pgSQL transaction control works only in top-level `CALL`/`DO` ([plpgsql-transactions.html#PLPGSQL-TRANSACTIONS](https://www.postgresql.org/docs/18/plpgsql-transactions.html#PLPGSQL-TRANSACTIONS)).

**Unique violations: no unconditional bucket.** 23505 may be transient, but "might represent persistent error conditions"; retry it only for diagnosed concurrent-key cases, and beware Serializable raising it even after an absence check ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html), [transaction-iso.html#XACT-SERIALIZABLE](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)).

**Three-attempt promise: no.** "Transaction retry does not guarantee that the retried transaction will complete"; high contention may need many attempts, and a conflicting prepared transaction can block progress indefinitely ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Any such bound is UNVERIFIED — support it with your own retry telemetry/SLO, not a PostgreSQL promise. Optionally also retry 40P01 deadlocks ([explicit-locking.html#LOCKING-DEADLOCKS](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-DEADLOCKS)).
