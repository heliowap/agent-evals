## Decision: No — the design is insufficient

**Isolation.** Repeatable Read (RR) in PostgreSQL is Snapshot Isolation, not serializability. It prevents phantoms — stronger than the SQL standard requires — but still permits **serialization anomalies** ([Table 13.1](https://www.postgresql.org/docs/18/transaction-iso.html#MVCC-ISOLEVEL-TABLE), [§13.2.2](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). The premise that "stable snapshot + no phantoms ⇒ serial-equivalent" is **incorrect**. The docs state RR views "will not necessarily always be consistent with some serial execution," and enforcing business rules at RR "is not likely to work correctly without careful use of explicit locks" ([§13.2.2](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ); [§13.4](https://www.postgresql.org/docs/18/applevel-consistency.html)). Cross-row read-then-write is exactly the read/write-conflict pattern that creates cycles ([§13.4](https://www.postgresql.org/docs/18/applevel-consistency.html)). If you need full read-write serializability, use **Serializable** (SSI) for all writes and consistent reads ([§13.4.1](https://www.postgresql.org/docs/18/applevel-consistency.html#SERIALIZABLE-CONSISTENCY)).

**Retry ownership and unit.** PostgreSQL "does not offer an automatic retry facility, since it cannot do so with any guarantee of correctness" — retry is the **application's** responsibility ([§13.5](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html#MVCC-SERIALIZATION-FAILURE-HANDLING)). The **retry unit is the whole transaction**, "including all logic that decides which SQL to issue and/or which values to use." Retrying only the failed statement is wrong: it will not replay the decision logic. SQLSTATE `40001` is the trigger.

**Unique violations.** Do **not** retry `23505` unconditionally. Only retry it when the violation reflects a concurrent duplicate (e.g., a key chosen from prior reads); otherwise it "might represent persistent error conditions" ([§13.5](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). `40001` may be retried unconditionally; consider `40P01` deadlocks.

**Three-attempt promise: No.** "Transaction retry does not guarantee that the retried transaction will complete; … with very high contention … completion may take many attempts," and a conflicting prepared transaction can block indefinitely ([§13.5](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Any such promise is **UNVERIFIED/unsupportable**; it would need a bounded concurrency/latency test against your actual workload to characterize, not a documentation guarantee.

**Recommended narrow changes:** (1) Use Serializable for invariant-affecting transactions, or keep RR and take explicit `SELECT FOR UPDATE`/`LOCK TABLE` before the snapshot freezes; (2) move retry to the application wrapping the full transaction; (3) gate `23505` retries on cause; (4) drop the 3-attempt SLA. Corroborating pages: [mvcc.html](https://www.postgresql.org/docs/18/mvcc.html), [transaction-iso.html](https://www.postgresql.org/docs/18/transaction-iso.html).
