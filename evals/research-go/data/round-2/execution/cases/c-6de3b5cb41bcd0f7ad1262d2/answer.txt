**Decision: fix four receiver/recovery items; do not promise exactly-once from GitHub alone.**

**1. Verify authenticity on raw bytes, before parsing.** Incoming evidence is the `X-Hub-Signature-256` header: an HMAC-SHA256 hex digest of the request body generated with your webhook secret; `X-Hub-Signature` (SHA-1) is legacy only. Because the digest covers the payload *contents*, your parse/re-serialize step changes the bytes and breaks verification — compute the HMAC on the raw body first, then parse and check event/action. GitHub also warns that proxies must not modify payload/headers ([validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries), [troubleshooting](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#troubleshooting)).

**2. Replace string equality with constant-time comparison.** Documented: "Never use a plain `==` operator"; use `secure_compare`, `crypto.timingSafeEqual`, or `hmac.compare_digest` ([same page](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries)).

**3. Correct the dedupe premise.** `X-GitHub-Delivery` is the GUID "to identify the event" ([delivery headers](https://docs.github.com/en/webhooks/webhook-events-and-payloads#delivery-headers)), and on redelivery it is *reused*: "If you request a redelivery, the X-GitHub-Delivery header will be the same as in the original delivery" ([best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header)); GitHub's own script notes "The GUID is constant across redeliveries" ([script](https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-github-app-webhook#adding-the-script)). Keying dedupe on GUID (not a per-attempt ID) is what makes legitimate redelivery idempotent; treat repeat GUIDs as replays.

**4. Timing/retry assumptions.** Respond 2XX within 10 seconds or GitHub terminates the connection and records a failure — so a synchronous 25-second job guarantees failures; return 202 and queue ([10-second rule](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds)). Safe: GitHub does **not** automatically redeliver failed deliveries; you must redeliver manually or by script, for deliveries from the past 3 days ([handling failures](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#about-webhook-delivery-failures), [redelivering](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks)). The outage-retry assumption is false.

**Exactly-once:** UNVERIFIED as documented. GUID/redelivery semantics give you at-least-once delivery with a dedupe key, but a crash after the business side effect and before recording the GUID can duplicate it; GitHub documents no transactional guarantee. Resolve via the REST redeliver-delivery endpoints (e.g. `docs.github.com/en/rest/apps/webhooks`) plus idempotency in your own datastore.
