## Decision: session contract

**Routing/session contract (documented facts):**
- Direct `env.DB.prepare().run()` never uses replicas; read replication requires the Sessions API on the Worker binding (not available via REST API) — otherwise all queries execute on the primary only. Sources: https://developers.cloudflare.com/d1/best-practices/read-replication/ and https://developers.cloudflare.com/d1/worker-api/d1-database/#withsession
- Checkout write request: open a session with `withSession("first-primary")` (or reuse a bookmark). Writes always go to the primary; `served_by_primary`/`served_by_region` in `result.meta` lets you verify routing (read-replication page, "Check where D1 request was processed").
- Later read request: pass the bookmark from the write session — return `session.getBookmark()` in the write response (e.g., an `x-d1-bookmark` header), then in the follow-up request call `env.DB.withSession(bookmark)`. The replica serving the read waits until it is *at least as up-to-date as that bookmark*, which is the documented "read my own writes" guarantee (sequential consistency: monotonic reads/writes, writes-follow-reads) — https://developers.cloudflare.com/d1/best-practices/read-replication/#replica-lag-and-consistency-model

**Correcting both premises:**
- **"first-primary pins the session to the primary" is wrong.** Only the *first query* of the session is directed to the primary; "Subsequent queries in the Session may use read replicas." (https://developers.cloudflare.com/d1/worker-api/d1-database/#withsession). Don't advertise the whole session as primary-pinned.
- **"withSession() always begins with the latest data" is also wrong.** `withSession()` ≡ `withSession("first-unconstrained")`, which routes the first query to *any* instance (primary or replica), explicitly for cases that don't need the latest data (read-replication page, "Start a session without constraints").

**Failure handling:** The team's expectation of partial commits is incorrect. `batch()` runs statements sequentially, non-concurrently, in autocommit — but "Batched statements are SQL transactions. If a statement in the sequence fails… it aborts or rolls back the entire sequence" (https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). So put the header insert and all line-item inserts in one `session.batch()` call: you get all-or-nothing semantics, and batch is also available on `D1DatabaseSession`. This removes the need for partial-commit recovery logic; on failure the session still exposes a bookmark from earlier successful queries for retries.

**Product's claims — what the docs support:**
- **Supported:** sequential consistency *within a session*, read-your-own-writes, and lower read latency/throughput when clients are near replicas in the six regions (ENAM, WNAM, WEUR, EEUR, APAC, OC; locations subject to change).
- **Not supported (recommend rejecting):** "globally latest reads" — replicas "may be arbitrarily out of date" outside a session/bookmark guarantee, and only the primary serves latest data. **"Maximum 100 ms replica-lag guarantee" is UNVERIFIED/unsupported:** no numeric lag SLA appears anywhere in the D1 docs (best-practices read-replication page, replica-lag sections). Next evidence target if Product insists: ask Cloudflare for a contractual lag commitment, or measure `served_by_region`-tagged latency empirically — neither establishes a documented guarantee.
