## Recommendation for Compose v2.18.0

**Documented facts** (per the two sources below):

1. **Startup ordering only.** With short-form `depends_on`, Compose only guarantees the dependency was *started* — it explicitly does not wait for readiness ([services reference, depends_on](https://docs.docker.com/reference/compose-file/services/#depends_on-short-syntax-1)); on startup Compose "does not wait until a container is 'ready', only until it's running" ([startup-order how-to](https://docs.docker.com/compose/how-tos/startup-order/#control-startup)). So convert the DB dependency to long syntax with `condition: service_healthy`, which requires the DB's `healthcheck` and blocks API creation until health passes.

2. **Migrations.** Use a one-shot service with `condition: service_completed_successfully` — the dependency must "run to successful completion" before the API starts. Make the migration service a true one-shot: `restart: "no"` (default) rather than `restart: always`, or it will loop instead of exiting 0. Note the short-syntax hint: intended equivalent `pre_start` init steps require Compose **5.3.0+**, unavailable here (UNVERIFIED for your cluster elsewhere: ["pre_start"](https://docs.docker.com/reference/compose-file/services/#pre_start)).

3. **Explicit operator restarts.** `restart: true` on the API's `depends_on.db` entry makes Compose restart the API after Compose-driven updates of the DB (e.g., `docker compose restart db`) — supported since **v2.17.0**, so v2.18.0 *does* support it ([depends_on long syntax](https://docs.docker.com/reference/compose-file/services/#depends_on-long-syntax-1)).

4. **Runtime restarts — cannot rely on this.** The reference states `restart: true` "applies to an explicit restart controlled by a Compose operation, and **excludes automated restart by the container runtime** after the container dies." So the assumption that a runtime-restarted (crashed) DB propagates to the API is **not documented for v2.18.0**. `restart: always` on the DB itself restarts *only the DB container* (it "always restarts the container until its removal" — [restart attribute](https://docs.docker.com/reference/compose-file/services/#restart)); it says nothing about dependents. Application-level connection-retry logic in the API is the only reliable mitigation; do not promise it from Compose alone.

5. **`required: false` for telemetry — unsupported at 2.18.0.** The `required` field on depends_on was "Introduced in Docker Compose version 2.20.0" ([depends_on long syntax](https://docs.docker.com/reference/compose-file/services/#depends_on-long-syntax-1)). On 2.18.0 this is UNVERIFIED/unsupported — either upgrade to ≥2.20.0 or model the telemetry optionality some other way (e.g., a separate profile).

**Lifecycle separation summary:** container start = `condition: service_started` (default semantics); readiness = `service_healthy` via healthcheck; successful migration = `service_completed_successfully`; explicit Compose restart propagation = `depends_on: restart: true` (2.17.0+); runtime crash restart propagation = **no guarantees on file**. Therefore this configuration alone **cannot justify promising the API remains ready to serve throughout later database failures** — health/restart propagation covers only Compose-initiated restarts, not daemon-driven recovery, so keep the availability promise out of any SLA unless you add application-level retry/readiness logic (recommendation, not a documented guarantee).
