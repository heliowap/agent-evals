## Decision: the design is not sufficient as proposed

**Correcting the premise.** Repeatable Read in PostgreSQL is Snapshot Isolation. It does give a transaction-start snapshot and does not exhibit phantom reads (stronger than the SQL standard's minimum for that level, which the standard permits), but Table 13.1 marks **serialization anomaly as still Possible** at Repeatable Read ([transaction-iso.html#TRANSACTION-ISO](https://www.postgresql.org/docs/18/transaction-iso.html#TRANSACTION-ISO)). A read-only transaction at this level can even see a control record updated while missing a logically related detail record; the docs state enforcing business rules at this level is "not likely to work correctly without careful use of explicit locks" ([same page, #XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). A read-then-write cross-row invariant is precisely the read/write-conflict cycle pattern described in [applevel-consistency.html#APPLEVEL-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#APPLEVEL-CONSISTENCY). So Repeatable Read does **not** make the combined decisions equivalent to serial execution.

**Fix that matters 1 — isolation.** Use Serializable (SSI): it adds nonblocking monitoring that rolls back transactions forming dangerous read/write cycles, and if *all* writes and all reads needing a consistent view run Serializable, "no other effort is required to ensure consistency" ([applevel-consistency.html#SERIALIZABLE-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#SERIALIZABLE-CONSISTENCY)). Alternative: Repeatable Read plus explicit locks (SELECT FOR UPDATE/LOCK TABLE **before** the snapshot is frozen), per [applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY). This is implementation-vs-standard: the standard defines Serializable as the strongest level; PostgreSQL emulates serial execution via SSI ([transaction-iso.html#XACT-SERIALIZABLE](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)).

**Fix 2 — retry ownership and unit.** The application/client must own retries; PostgreSQL "does not offer an automatic retry facility, since it cannot do so with any guarantee of correctness," and you "must retry the complete transaction, including all logic that decides which SQL to issue" ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Statement-level retry is wrong.

**Fix 3 — unique violations are not unconditionally retryable.** SQLSTATE 40001 (serialization_failure) may be retried unconditionally; 40P01 deadlocks advisably. But 23505 unique_violation "may" be retried only in some cases (e.g., concurrently chosen keys the server cannot link to earlier reads — effectively a serialization failure); such errors "might represent persistent error conditions," so inspect the cause rather than blind-retry ([same page]). Note SSI can still raise 23505 after a checked insert unless all inserting transactions follow the check-first protocol ([transaction-iso.html#XACT-SERIALIZABLE](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)).

**Three-attempt SLA: cannot be promised.** The docs explicitly state retry "does not guarantee that the retried transaction will complete," that high contention may need many attempts, and a conflicting prepared transaction may block progress until resolved ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Document behavior/p99 trejectories, not a universal commit guarantee.
