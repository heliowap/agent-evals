## Decision

**Isolation choice:** Repeatable Read is **not sufficient** for your cross-row invariant. RR gives a stable snapshot and no phantom reads, but the docs explicitly warn it "may see ... data ... not consistent with some serial execution" and that "attempts to enforce business rules by transactions running at this isolation level are not likely to work correctly without careful use of explicit locks" ([transaction-iso.html#XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). Under Snapshot Isolation, two transactions can both read old values of the *other's* rows and both commit — a write-skew serialization anomaly — because PostgreSQL at RR only detects conflicts on rows being modified, not read/write dependencies. Serializable (SSI) adds exactly those read/write dependency checks and aborts one side with error 40001. **Use Serializable**, not RR.

**Recovery unit:** The docs are unambiguous: "It is important to retry the complete transaction, including all logic that decides which SQL to issue and/or which values to use. Therefore, PostgreSQL does not offer an automatic retry facility" ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Replaying only the failed statement is wrong: the snapshot, sequence/ID generation, and earlier decision logic are not automatically re-derived. **Ownership:** your application owns retrying. **Unit:** the whole transaction from the first statement.

**Error-code policy:** Retry `40001` (serialization_failure) and typically `40P01` (deadlock) unconditionally. Unique-key failures (`23505`) may be serialization failures under the hood ("effectively a serialization failure, but the server will not detect it as such"), but doc says "more care is needed when retrying these other error codes, since they might represent persistent error conditions" — so a generic wrapper must **not** blanket-retry all 23505. Retrying can hide a genuine duplicate (e.g., re-insert of a really conflicting key), causing loops or corrupted state. Retry 23505 only when the code path provably derives keys from prior reads, or use `ON CONFLICT` with idempotent semantics; otherwise surface it.

**Three-attempt SLA:** You **cannot** make that promise. Docs: "multiple retries may be needed. In cases with very high contention, it is possible that completion of a transaction may take many attempts" ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Document instead a retry *policy* (bounded attempts with backoff, then defer/queue failure) — that it responds within N attempts, not that it commits.

**Recommendations:** Serializable + full-transaction retry on 40001/40P01 (and vetted 23505); keep transactions small and READ ONLY where possible ([transaction-iso.html#XACT-SERIALIZABLE](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)).
