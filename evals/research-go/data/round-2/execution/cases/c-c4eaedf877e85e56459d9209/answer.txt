## Decision: insufficient as designed — three corrections

**1. Corrected premise — Repeatable Read does not give serial equivalence.** PostgreSQL's RR is Snapshot Isolation: it guarantees a stable snapshot and (stronger than the SQL standard's minimum) prevents phantom reads, but Table 13.1 shows serialization anomalies remain *possible* at RR (https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ). The SQL standard defines levels as *minimum* phenomena prohibitions; absence of phantoms is not absence of serialization anomalies. The doc explicitly warns business-rule enforcement at RR is "not likely to work correctly without careful use of explicit locks" (https://www.postgresql.org/docs/18/applevel-consistency.html#APPLEVEL-CONSISTENCY). A read-then-write invariant across rows is exactly the read/write-conflict cycle that only Serializable detects; without it, integrity checks "will not work correctly" when concurrent transactions interleave reads and writes (https://www.postgresql.org/docs/18/applevel-consistency.html#SERIALIZABLE-CONSISTENCY).

**2. Retry unit = the whole transaction, owned by the application.** Pg 13.5 is explicit: retry "the complete transaction, including all logic that decides which SQL to issue and/or which values to use"; PostgreSQL deliberately offers *no* automatic retry server-side because it cannot guarantee correctness (https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html#MVCC-SERIALIZATION-FAILURE-HANDLING). Retrying only the failed statement is wrong — the earlier decision logic ran against a now-invalid snapshot and will not be "replayed" automatically; the wrapper must re-run decision logic from a fresh snapshot. Only updating transactions need retrying; read-only ones never hit serialization conflicts (transaction-iso, §13.2.2).

**3. Retry bucket must be causal, not error-class-generic.** 40001 serialization_failure: docs recommend retrying unconditionally. 40P01 deadlock: advisable to retry. 23505/23P01 unique/exclusion: *sometimes* appropriate, "more care is needed... they might represent persistent error conditions" — so unique violations must **not** sit in an unconditional retry bucket; classify per-statement/per-constraint with cause inspection, and only treat as transient known-concurrency patterns (13.5). Even under Serializable, unique_violation can occur for serially impossible conflicts unless *all* transactions inserting those keys check first (https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE).

**Narrow changes.** Use Serializable for all writes and all reads needing a consistent view, ideally via a framework that auto-retries (13.4.1, recommendation); or keep RR and take explicit locks before the first data command (RR's snapshot freezes at the first query/UPDATE/DELETE/MERGE) (https://www.postgresql.org/docs/18/applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY, recommendation).

**Product promise (≤3 attempts): cannot be documented as a guarantee.** Docs state retries don't guarantee completion; under high contention *many* attempts may be needed, and a conflicting prepared transaction can block progress until it resolves (13.5). Promise only a best-effort SLO with escalation/fallback — any hard commit-within-N-attempts claim contradicts documented behavior (UNVERIFIED as achievable; a latency/throughput measurement plan plus deadlocking-prepared-transaction policy would be what product needs, not a server guarantee).
