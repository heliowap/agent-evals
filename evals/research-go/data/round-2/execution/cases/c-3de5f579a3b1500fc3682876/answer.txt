## Decision: Do not deploy. The Permission Model does **not** certify tenant isolation for untrusted code.

**Core premise (incorrect).** The security policy and the v24.21.0 permissions docs both state the model is a "seat belt" for *trusted* code: "malicious code can bypass the permission model and execute arbitrary code," and running customer-uploaded JavaScript makes that code a trusted element — such bypass is not even a Node.js vulnerability ([permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permissions); [SECURITY.md "Permission Model Boundaries"](https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md)). Tenant isolation must come from OS-level boundaries (separate users/containers); `--permission` is useful only as defense-in-depth for *your trusted launcher/orchestrator* code.

**Assumptions that must change:**

1. **`--allow-fs-read=/srv/jobs/*.js` is broader than intended.** After a wildcard all subsequent characters are ignored, so `*.js` behaves like `/srv/jobs/*` — every file in the directory tree is readable, not just `.js` ([File System Permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#file-system-permissions)). Also note behavior if the directory does not exist when the wildcard is appended.
2. **Relative symlinks in job directories defeat the read list.** Symlinks are followed even outside granted paths; docs explicitly require ensuring granted paths contain no relative symlinks ([Limitations and Known Issues](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#limitations-and-known-issues)). With attacker-controlled job dirs this is a documented escape; the model must not be treated as compensating here.
3. **`--env-file` is not subject to the model.** It reads files before the model initializes, so the env file outside the read list is still loaded — documented, but it means the read list is not the effective secret-exposure surface ([Permission Model constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)).
4. **The passed-in file descriptor bypasses the model.** "Using existing file descriptors via the node:fs module bypasses the Permission Model" — same constraints section. Anything readable through that fd is outside enforcement.
5. **Other unmodeled channels exist:** `node:sqlite` file access, `process._debugProcess()` (can force another same-OS-user Node process to open its Inspector), OpenSSL STORE loaders if granted, and `permission.drop()` does not revoke already-open resources.

**Worker inheritance — inconsistent between the two sources.** The permissions page's constraints section states "The model does not inherit to a worker thread," while the security policy states workers *inherit* the parent's permission restrictions and that modified `execArgv` grants nothing extra. I can't silently pick one; this conflict is **UNVERIFIED** from these two pages. Resolve it empirically on v24.21.0 (e.g., audit-mode diagnostics on a worker with restricted grants) before relying on either statement. Even the favorable reading doesn't help deployment, since the parent boundary itself fails.

**Useful mechanisms for trusted code only:** audit mode with its diagnostics-channel reporting (`node:permission-model:fs`, etc.) to discover least-privilege grants before enforce mode; `permission.has()`/`drop()`; enforce mode for the orchestrator that never runs customer code.

**Certification:** No — the documents explicitly disclaim security guarantees for this model, and several launcher choices (wildcard breadth, symlinks, env-file, fd, possibly workers) break it further. Propose OS/container-per-tenant isolation with `--permission` only as hardening for trusted code.
