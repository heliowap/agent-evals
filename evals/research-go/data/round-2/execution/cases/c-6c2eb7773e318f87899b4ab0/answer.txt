## Decision: fix four things before launch

**1. Verify before parsing (authenticity evidence).** The only documented proof of origin is the `X-Hub-Signature-256` HMAC-SHA256 signature, computed from your webhook secret over the payload contents. Validate against the **raw request body** — your parse-and-reserialize step will change byte formatting and make the signature mismatch, so verification must run on the original bytes first. GitHub explicitly says never to use a plain `==`; use a constant-time comparison (e.g., `hmac.compare_digest`, `crypto.timingSafeEqual`), and expect the `sha256=` prefix. [Validating webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries). A valid signature establishes "sent by GitHub and not tampered with"; it is not, by itself, a replay defense.

**2. Respond within 10 seconds.** GitHub terminates the connection and records a failure if your server takes longer than 10 seconds to return 2XX — a 25-second inline job guarantees every delivery "fails." Documented pattern: enqueue work asynchronously and respond immediately. [Best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds), [Handling deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-webhook-deliveries#write-code-to-handle-webhook-deliveries). *(Recommendation: verify signature, dedup-check, persist, then 202.)*

**3. Correct the retry premise.** GitHub does **not** automatically redeliver failed deliveries; redelivery is manual (repo admins, deliveries from the past 3 days) or via your own scheduled script calling the REST API, with a PAT (webhook write) or GitHub App — the workflow `GITHUB_TOKEN` lacks permission. [Handling failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#handling-delivery-failures), [Redelivering webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks). Rebuild the recovery plan around the scripted redelivery pattern ([repository script example](https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-repository-webhook#adding-the-script)).

**4. Fix the dedup key.** Premise incorrect: on a requested redelivery, the `X-GitHub-Delivery` GUID is **the same** as the original delivery; the GUID is constant across redeliveries, while per-attempt delivery IDs differ. Key deduplication on the delivery GUID. [Best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header), [redelivery script](https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-repository-webhook#adding-the-script).

## Exactly-once across a crash?

**No — the documented mechanisms alone cannot justify it.** Signature + GUID dedup gives per-delivery authenticity and de-duplication of redeliveries, but GitHub's docs promise no exactly-once delivery semantics, and a crash between enqueue and dedup-mark can still double-process. At-least-once with dedup is what you can reasonably claim; make the business effect itself idempotent keyed on the delivery GUID. UNVERIFIED: whether your dedup store survives a crash between receive and persist — that requires an atomic (transactional) enqueue-plus-mark, which no GitHub doc addresses.
