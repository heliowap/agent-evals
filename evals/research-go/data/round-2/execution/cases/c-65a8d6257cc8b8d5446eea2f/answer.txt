## Decision: Not sufficient as designed — use Serializable, retry whole transactions, and reject the three-attempt promise

**1. Repeatable Read does not make cross-row invariant checks equivalent to serial execution.**
The workload (read rows to evaluate a business invariant, then update different rows) is exactly the read/write conflict pattern the docs warn about: under Repeatable Read (Snapshot Isolation) two such transactions can form a cycle and both commit, producing an anomaly ([transaction-iso §13.2.2](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ), [applevel-consistency §13.4](https://www.postgresql.org/docs/18/applevel-consistency.html#APPLEVEL-CONSISTENCY)). The docs explicitly say attempts to enforce business rules at this level are "not likely to work correctly without careful use of explicit locks." The docs also stress that a stable snapshot is not necessarily consistent with any serial order. Repeatable Read exceeds the SQL *standard's minimum* for that level (postgreSQL also forbids phantoms there, while the standard permits them) — but no standard level except Serializable rules out serialization anomalies, which RR explicitly allows ([table 13.1](https://www.postgresql.org/docs/18/transaction-iso.html#MVCC-ISOLEVEL-TABLE)).

**Recommendation (my view, based on the documented trade-offs):** Use Serializable for all transactions that read the invariant. An alternative is Repeatable Read plus explicit locks taken *before* the snapshot freezes (§13.4.2), but that blocks more.

**2. Statement-level retry is wrong; retry ownership and unit.**
On any SQLSTATE `40001` (serialization_failure), the application "should abort the current transaction and retry the whole transaction from the beginning" ([§13.2.2](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). PostgreSQL provides **no automatic retry facility, since it cannot do so with any guarantee of correctness** — retrying only the failed statement cannot work, because the entire decision logic must re-read fresh data ([§13.5](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). The application/framework owns retrying the *complete* transaction.

**3. Unique-key violations must not be retried unconditionally.**
`23505` unique_violation is sometimes an effective serialization failure (e.g., duplicate key chosen concurrently), which is why a checklist including it is advisable — but §13.5 warns these codes "might represent persistent error conditions rather than transient failures," so more care is needed than the unconditional retry the docs recommend only for `40001` (and optionally `40P01` deadlock). Vet cause per call site; don't blanket-retry.

**4. The three-attempt commit promise cannot be documented.**
§13.5 states retry does not guarantee completion; "multiple retries may be needed," and under very high contention many attempts (or blocking on a prepared transaction) may be required. **UNVERIFIED / unresolvable from docs:** any bounded-attempt guarantee. Next evidence target: none in PostgreSQL docs — the promise must be engineered (e.g., bounded retries with backoff to a queue/timeout) and framed as a product SLA, not a database property.
