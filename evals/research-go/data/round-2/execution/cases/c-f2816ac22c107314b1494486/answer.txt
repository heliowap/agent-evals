**Decision: do not deploy this as a tenant-isolation boundary.** The documentation forbids that use, and several specific assumptions are wrong.

**Incorrect premises**

1. *"Sole tenant-isolation boundary."* The model "does not protect against malicious code… Malicious code can bypass the permission model and execute arbitrary code without the restrictions imposed" ([permissions.html#permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permissions)). SECURITY.md states `--permission` "is designed to reduce the blast radius of mistakes in trusted application code, **not** to act as a security boundary against intentional misuse or a compromised process" ([SECURITY.md](https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md), "Permission Model Boundaries (`--permission`)").
2. *Staging on `--permission-audit` proves nothing about production:* audit mode performs no denial — violations are only published to diagnostics channels — and if both flags are passed, `--permission` wins ([#audit-mode](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#audit-mode)).
3. *`--allow-fs-read=/srv/jobs/*.js` does not restrict to `.js`:* "After passing a wildcard character (*) all subsequent characters will be ignored," so it behaves as `/srv/jobs/*` ([#file-system-permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#file-system-permissions)).
4. *Relative symlinks in job directories are a documented hole:* "Symbolic links will be followed even to locations outside of the set of paths that access has been granted to. Relative symbolic links may allow access to arbitrary files" ([#limitations-and-known-issues](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#limitations-and-known-issues)). Untrusted-writable job dirs therefore defeat the read list.
5. *`--env-file` is outside the model* (loaded before permission initialization), so secrets land in `process.env` readable by the job ([#permission-model-constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)); and *passing an open fd bypasses the model entirely* ("Using existing file descriptors via the node:fs module bypasses the Permission Model").
6. `--allow-worker` also exposes ungated `process._debugProcess(pid)` ([#process_debugprocess](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#process_debugprocess-and-cross-process-inspector-activation)).

**Worker inheritance — genuinely conflicting, UNVERIFIED.** permissions.html says "The model does not inherit to a worker thread" ([#permission-model-constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)), while SECURITY.md says "Workers inherit the permission restrictions of their parent process… Passing an empty or modified `execArgv` does not grant additional permissions." worker_threads.html only says `execArgv` is inherited by default ([worker_threads.html#new-workerfilename-options](https://nodejs.org/download/release/v24.21.0/docs/api/worker_threads.html#new-workerfilename-options)). Do not assume exact inheritance; resolve via the v24.21.0 test suite or a Node.js issue.

**Recommendation (not documented fact):** use separate OS users/containers, seccomp/AppArmor, and per-tenant process isolation, as the same page suggests; keep the Permission Model as defense-in-depth for trusted code only. **No, these documents do not let you certify tenant isolation.**
