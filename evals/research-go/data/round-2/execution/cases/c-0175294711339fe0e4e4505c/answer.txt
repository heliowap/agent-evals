## Decision: Not deployable as proposed. The permission model cannot certify tenant isolation — by documented design.

**Core premise is incorrect.** The Node.js threat model trusts the code it is asked to run: "The code run inherits all the privileges of the execution user," and the permissions doc states the model "does not protect against malicious code… Malicious code can bypass the permission model and execute arbitrary code" ([permissions.html#permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permissions); [SECURITY.md — Permission Model Boundaries](https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md)). SECURITY.md explicitly classifies `--permission` misuse as a non-vulnerability. Customer-uploaded JS must not be placed inside the trusted code domain; per-tenant OS isolation (separate users, seccomp/AppArmor, per docs' own guidance on `process._debugProcess()`) is required.

**Assumptions requiring change (documented facts):**
1. **Wildcards truncate:** `/srv/jobs/*.js` is treated as `/srv/jobs/*` — "After passing a wildcard character (*) all subsequent characters will be ignored," so all reads, not just `.js`, are allowed ([permissions.html#file-system-permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#file-system-permissions)).
2. **Symlinks:** "Symbolic links will be followed even to locations outside of the set of paths that access has been granted to. Relative symbolic links may allow access to arbitrary files" — you must guarantee no relative symlinks in granted paths ([permissions.html#limitations-and-known-issues](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#limitations-and-known-issues)).
3. **`--env-file` bypasses the model entirely** (it reads before environment initialization) — the env file is unguarded ([permissions.html#permission-model-constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)).
4. **Pre-opened file descriptors bypass the model** via `node:fs`; `permission.drop()` likewise "does not close or revoke access to resources that are already open" ([permissions.html#permissiondropscope-reference](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permissiondropscope-reference)).
5. **Audit mode denies nothing** — it only publishes violations to diagnostics channels; it cannot be a production boundary. If both `--permission` and `--permission-audit` are passed, `--permission` takes precedence ([permissions.html#audit-mode](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#audit-mode)).
6. **Other documented bypasses:** `node:sqlite`/`ATTACH DATABASE` fs access is not intercepted; OpenSSL STORE loaders are unconstrained by fs scopes ([permissions.html#file-system-permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#file-system-permissions); [SECURITY.md](https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md)).

**Worker inheritance — stated limitation, not a silent choice:** the version-matched sources conflict. permissions.html#permission-model-constraints states "The model does not inherit to a worker thread," while SECURITY.md's Permission Model Boundaries section states workers inherit the parent's restrictions and modified `execArgv` grants nothing. Resolving this requires the v24.21.0 `worker_threads` docs / changelog behavior tests. Until then, treat worker inheritance as **UNVERIFIED** — and irrelevant to the decision, since the model isn't a security boundary regardless.

**Useful for trusted code:** `--permission` as defense-in-depth against your own operator/launcher mistakes; `--permission-audit` in staging to discover required grants; `permission.has()`/`drop()` to scope trusted initialization paths.

**Certification verdict:** No. These documents affirmatively establish that `--permission` is not a tenant-isolation mechanism for untrusted code.
