## Decision

Not sufficient as proposed. Change three things: use Serializable with whole-transaction retries (or keep Repeatable Read plus explicit locks), never retry a single statement, and never bucket 23505 unconditionally.

**Correct premises first.** PostgreSQL's Repeatable Read already forbids phantom reads — stronger than the SQL standard's minimum, which permits them; that extra strength is still not serializability ([transaction-iso.html#XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). A stable snapshot prevents phantoms but not serialization anomalies: read/write conflicts can create a cycle in apparent execution order, so "attempts to enforce business rules by transactions at this isolation level are not likely to work correctly without careful use of explicit locks" ([transaction-iso.html#XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ), [applevel-consistency.html#APPLEVEL-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#APPLEVEL-CONSISTENCY)). Serializable is Repeatable Read plus nonblocking monitoring that rolls back one transaction to break such cycles ([applevel-consistency.html#SERIALIZABLE-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#SERIALIZABLE-CONSISTENCY)).

**Who retries, and what unit.** The application owns retry; PostgreSQL "does not offer an automatic retry facility, since it cannot do so with any guarantee of correctness" ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Retry the complete transaction, "including all logic that decides which SQL to issue and/or which values to use" — so the failed-statement retry expecting replay of decision logic is wrong ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)).

**Unique violations.** 23505 may be retryable when it genuinely masks a serialization conflict, but "more care is needed … since they might represent persistent error conditions rather than transient failures"; only 40001 is recommended for unconditional retry ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Classify by cause; surface deterministic duplicates.

**Locks alternative.** If staying on Repeatable Read, acquire required locks before the first query freezes the snapshot ([applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY)).

**Three-attempt guarantee: cannot promise.** Retries may need many attempts under high contention, and a conflicting prepared transaction may block progress until it resolves ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). UNVERIFIED: any per-attempt success probability would require your own contention measurements; PostgreSQL documents no bound.
