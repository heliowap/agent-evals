## Decision: session + failure contract

**Routing contract**
- Do **not** pin every request to `first-primary` — that defeats replication for most reads. Only the first query of a session is directed to the primary; subsequent queries may use replicas, so over-use mostly just degrades first-read latency.
- For the checkout path, carry the D1 **bookmark** across HTTP requests (e.g., `x-d1-bookmark` response/request header) and start each request's session with `withSession(bookmark)`, falling back to `"first-unconstrained"` when absent. Starting a session with a prior session's bookmark guarantees the session is at least as up-to-date as that bookmark, so the later read request sees the checkout write — the documented "read my own writes" / "read-follows-write" property of sequential consistency. If a request has no prior bookmark and truly needs latest data, use `"first-primary"` for that request's first query; writes always go to the primary regardless ([read-replication](https://developers.cloudflare.com/d1/best-practices/read-replication/#start-a-session-from-previous-context-bookmark), [#withsession](https://developers.cloudflare.com/d1/worker-api/d1-database/#withsession)).
- Correct the premises: `withSession()` equals `"first-unconstrained"` — the first query routes to *any* instance and is explicitly **not** guaranteed to start with the latest data. Conversely, `withSession("first-primary")` is **not** "the entire session pinned to the primary" — only the first query is directed at the primary; the session as a whole provides sequential consistency, not primary pinning ([withsession params](https://developers.cloudflare.com/d1/worker-api/d1-database/#parameters-4)).

**Batch failure handling — correct the premise**
- `session.batch()` is a SQL transaction: if any statement fails, the error identifies that statement and **the entire sequence aborts/rolls back** — earlier statements do *not* remain committed ([batch()](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch-1:~:text=Batched%20statements%20are)). So the team's expectation is wrong; use batch's atomicity rather than designing for partial commits. If partial-commit semantics are truly required, issue separate statements and handle recovery in app code (recommendation, not a documented guarantee).

**What the docs support / don't**
- Supported to advertise: read replication lowers read latency and scales read throughput; Sessions API provides **sequential consistency** (monotonic reads/writes, read-your-own-writes) within a session via bookmarks; writes always go to the primary ([replica lag model](https://developers.cloudflare.com/d1/best-practices/read-replication/#sessions-api-provides-sequential-consistency)).
- **Not supported**: "globally latest reads" — `first-unconstrained` explicitly does not guarantee latest data, and `first-primary` only constrains the *first* query. Also **not supported**: a "maximum 100 ms replica-lag guarantee." The docs state replicas are asynchronously replicated and "may be arbitrarily out of date," with no lag bound anywhere ([#primary-vs-replicas](https://developers.cloudflare.com/d1/best-practices/read-replication/#primary-database-instance-vs-read-replicas)). What would resolve this: a documented SLA on replica lag in official D1 docs (none exists in fetched pages); otherwise word marketing as "sequentially consistent reads near you, with read-after-write guaranteed via sessions."
