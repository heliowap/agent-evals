## Decision: fix the receiver, not just the retry story

**Incorrect premises.** GitHub does **not** automatically retry failed deliveries after an outage: "GitHub does not automatically redeliver failed deliveries" ([handling failures](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#about-webhook-delivery-failures)). And redelivery does **not** mint a new delivery ID: "If you request a redelivery, the X-GitHub-Delivery header will be the same as in the original delivery" ([best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header)).

**Minimum receiver changes**
1. Verify before parsing. Compute HMAC-SHA256 over the **raw** request body and compare with `X-Hub-Signature-256` using constant time (`hmac.compare_digest`/`crypto.timingSafeEqual`); note GitHub's own examples verify then parse. Docs explicitly warn never to use plain `==`, to treat bodies as UTF-8, and not to modify payload/headers pre-verification ([validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries)). Authenticity comes from the shared secret plus this digest; parsing/re-serializing destroys it.
2. Ack in under 10 seconds. GitHub terminates the connection and records **failure** if the server exceeds that; docs recommend a queue and asynchronous processing ([best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds)). Enqueue the verified raw payload, return 2XX, run the 25-second job off-request.
3. Key dedupe/idempotency on `X-GitHub-Delivery`, the GUID that identifies the delivery ([delivery headers](https://docs.github.com/en/webhooks/webhook-events-and-payloads#delivery-headers)). Since a redelivery reuses that GUID, the current "new ID ⇒ new event" rule is wrong; treat a same-GUID re-arrival as a replay of one logical event, and make the business side effect idempotent (durable "processed" marker committed with the effect).
4. Redelivery recovery is operator/script-driven within the 3-day window: list deliveries via REST, find non-OK statuses, and call the redeliver endpoints ([redelivering webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks), [handling failures](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#handling-delivery-failures)). Schedule this reconciliation; add alerting on the 10-second failure signal.

**Exactly-once:** No. Documented mechanisms give authenticity/integrity and a reusable delivery ID, but no exactly-once guarantee — the side-effect guarantee depends on your transactional idempotency design. A receiver crash between effect and marker is **UNVERIFIED** by GitHub docs; resolve via the REST delivery/delivery-status audit trail plus your own idempotency tests.
