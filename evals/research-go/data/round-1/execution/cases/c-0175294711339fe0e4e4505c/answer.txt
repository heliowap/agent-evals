## Decision: Not deployable as described — the Permission Model cannot be the sole tenant-isolation boundary

**Core premise correction.** The v24.21.0 permissions doc states the model "does not protect against malicious code… Malicious code can bypass the permission model and execute arbitrary code" ([permissions.html](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permissions)). SECURITY.md agrees: the model reduces "the blast radius of mistakes in trusted application code, **not** … a security boundary against intentional misuse," and Node trusts "the code it is asked to run" ([SECURITY.md](https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md)). Customer-uploaded JS is untrusted by definition → **you cannot certify tenant isolation from these documents; certification is impossible with this design.**

**Assumptions requiring change (documented):**
1. **Audit ≠ enforcement.** `--permission-audit` performs checks but "access is not denied"; violations only go to diagnostics channels ([permissions.html#audit-mode](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#audit-mode), [cli.html#--permission-audit](https://nodejs.org/download/release/v24.21.0/docs/api/cli.html#--permission-audit)). Fine for staging discovery; production must use `--permission` (if both given, `--permission` wins).
2. **`*.js` glob is an illusion.** "After passing a wildcard character (*) all subsequent characters will be ignored. For example: /home/*.js will work similar to /home/*" — your grant is effectively `/srv/jobs/*`, all files ([permissions.html#file-system-permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#file-system-permissions)). Entry points are also implicitly readable ([cli.html#--allow-fs-read](https://nodejs.org/download/release/v24.21.0/docs/api/cli.html#--allow-fs-read)).
3. **Symlinks break the read list.** "Relative symbolic links may allow access to arbitrary files"; you "must ensure that no paths to which access has been granted contain relative symbolic links" ([permissions.html#limitations-and-known-issues](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#limitations-and-known-issues)). Your symlinked job dirs violate this directly — sanitize or forbid them.
4. **`--env-file` is outside the model** ("not subject to the rules of the Permission Model") and its values land in `process.env`, which workers copy by default ([permissions.html#permission-model-constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints), [cli.html#--env-filefile](https://nodejs.org/download/release/v24.21.0/docs/api/cli.html#--env-filefile)). Secrets in it are readable by job code; env-file values could also set `NODE_OPTIONS`.
5. **Pre-opened FDs bypass the model**: "Using existing file descriptors via the node:fs module bypasses the Permission Model" ([constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)).
6. **`--allow-worker` plus documented bypasses**: `node:sqlite` SQL file access isn't intercepted, and `process._debugProcess()` isn't gated by any scope — it can force another Node process on the same host/OS user to open its inspector; the docs say to use different OS users/OS-level isolation ([permissions.html#process_debugprocess-and-cross-process-inspector-activation](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#process_debugprocess-and-cross-process-inspector-activation)).

**Worker inheritance — UNVERIFIED/conflicting.** permissions.html says "The model does not inherit to a worker thread" ([constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)), but SECURITY.md says "Workers inherit the permission restrictions of their parent process. Passing an empty or modified `execArgv` … does not grant it additional permissions" ([SECURITY.md](https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md)). The worker_threads page only documents `execArgv` defaulting to parent inheritance, not permissions ([worker_threads.html#new-workerfilename-options](https://nodejs.org/download/release/v24.21.0/docs/api/worker_threads.html#new-workerfilename-options)). No consistent answer exists in these sources; resolve via a version-matched empirical test or the `process.permission` docs/tests before relying on either claim.

**Useful for trusted code only:** `--permission-audit` (permission discovery), `process.permission.has()/drop()` (irreversible, can't close open FDs), `--allow-child-process` flag propagation via `NODE_OPTIONS`, `worker.resourceLimits` (JS heap only). For real tenant isolation, run separate OS users/containers per tenant and keep the Permission Model as defense-in-depth.
