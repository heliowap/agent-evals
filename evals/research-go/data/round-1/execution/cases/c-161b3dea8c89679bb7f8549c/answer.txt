## Decision: fix three defects, rewrite the recovery plan

Your authenticity premise is broken. GitHub computes the HMAC-SHA256 signature over the **raw payload contents**, and warns "Make sure that the payload and headers are not modified before verification" — proxies/load balancers must not alter them ([validating-webhook-deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries)). Parsing JSON and re-serializing changes bytes, so verification will fail (or, worse, you may verify a re-serialized copy). Verify the raw body first, then parse. Also replace ordinary `==` with a constant-time compare (`crypto.timingSafeEqual`, `hmac.compare_digest`); GitHub documents this explicitly ([same section](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries)). The only incoming authenticity evidence is the HMAC signature from your webhook secret; the `X-GitHub-Delivery` header is an identity/replay key, not an authenticity proof ([best-practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header)).

**Timing:** respond 2XX within 10 seconds or GitHub terminates the connection and records a failure ([best-practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds)). A 25-second job inline guarantees failure; enqueue immediately, process asynchronously.

**Retry assumption is wrong.** GitHub "does not automatically redeliver failed webhook deliveries" ([handling-failed-webhook-deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#about-webhook-delivery-failures)). Recovery is manual or via the redeliver API, limited to the past 3 days ([redelivering-webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks)).

**Identifier behavior:** the `X-GitHub-Delivery` header (the delivery GUID) "will be the same as in the original delivery" on redelivery ([best-practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header)). Your dedup store is therefore backwards: key on that GUID, treating a redelivery as the **same** event, not a new one. GitHub's own recovery script groups by GUID to prevent duplicate/feedback redelivery ([repository-webhook script](https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-repository-webhook#adding-the-script)).

**Recommendation (minimum):** (1) verify raw body with constant-time compare; (2) 2XX + async queue; (3) dedupe on delivery GUID. Then run a scheduled job using the delivery list/redeliver APIs to recover failures within 3 days.

**Exactly-once?** No. Documented mechanisms give authenticity and a stable idempotency key only. Across a receiver crash between processing and acknowledgment, dedup on the GUID plus an atomic side-effect store is required — the docs make no transactional guarantee. **UNVERIFIED**: consult [REST endpoints for repository webhooks](https://docs.github.com/en/rest/repos/webhooks) to confirm delivery ordering/atomicity limits.
