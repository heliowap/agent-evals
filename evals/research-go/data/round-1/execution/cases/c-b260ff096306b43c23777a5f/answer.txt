## Decision

**Minimum receiver changes**

1. **Verify HMAC-SHA256 on the raw body before parsing.** The signature is an HMAC hex digest over the payload contents using your webhook secret, sent as `X-Hub-Signature-256`; never use plain `==` — use a constant-time comparison (`secure_compare`, `hmac.compare_digest`, `crypto.timingSafeEqual`). Docs warn the payload and headers must not be modified before verification, so parse-after-verify and drop re-serialization. ([Validating webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries))
2. **Acknowledge first, process later.** Return 2XX within 10 seconds; slower responses are terminated and recorded as failures. Queue the 25-second job. ([Best practices: Respond within 10 seconds](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds))
3. **Deduplicate on `X-GitHub-Delivery`, and treat requested redelivery as the same event.** Your premise is wrong: on redelivery that header matches the original delivery. GitHub's redelivery script explicitly groups by GUID because "the GUID is constant across redeliveries of the same delivery," and dedupes per GUID. ([Best practices: X-GitHub-Delivery header](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header); [redelivery script](https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-repository-webhook#adding-the-script))

**Recovery plan correction:** the ops assumption is wrong. "GitHub does not automatically redeliver failed deliveries"; you must redeliver manually or via a scheduled REST API script, and only deliveries from the past 3 days are redeliverable. Schedule that script, dedupe by GUID, and investigate repeated failures. ([Handling failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#about-webhook-delivery-failures); [Redelivering webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks))

**Authenticity evidence:** the valid `X-Hub-Signature-256` over the exact raw bytes, plus a high-entropy stored secret. The GUID proves delivery identity/replay uniqueness, not authenticity.

**Exactly-once:** No. These documented mechanisms give authenticated, deduplicable, at-least-once delivery only; GitHub documents no exactly-once guarantee. HMAC validates origin/integrity, and GUID dedup collapses redeliveries, but a crash between side effect and dedup-store commit can still duplicate or lose work. UNVERIFIED without a documented transactional boundary; resolve by making effects idempotent keyed on GUID (transactional dedup/outbox) and confirming via a failure-injection test — GitHub docs cannot close this gap.
