## Decision: change four things before launch

**1. Verify the raw bytes first, then parse.** GitHub computes the digest over "the payload contents" with your secret and sends it as `X-Hub-Signature-256`; compare it with a constant-time function — docs explicitly say "Never use a plain `==` operator" — and "make sure that the payload and headers are not modified before verification" ([validating-webhook-deliveries#validating-webhook-deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries), [#troubleshooting](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#troubleshooting)). So your current order is backwards: parse/re-serialize after verification, never before. Authenticity evidence is exactly this HMAC-SHA256 header (a configured secret is required); IP allow-listing and HTTPS are supplementary, not substitutes ([best-practices#allow-githubs-ip-addresses](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#allow-githubs-ip-addresses)).

**2. Acknowledge before the 25-second job.** "Your server should respond with a 2XX response within 10 seconds… If your server takes longer… GitHub terminates the connection and considers the delivery a failure" ([#respond-within-10-seconds](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds)). Verify → durably enqueue → 2XX → process asynchronously. Never return success only after the job.

**3. Correct the redelivery-identifier premise.** Redelivery keeps the same GUID: "If you request a redelivery, the `X-GitHub-Delivery` header will be the same as in the original delivery" ([#use-the-x-github-delivery-header](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header)); it is "a globally unique identifier (GUID) to identify the event" ([webhook-events-and-payloads#delivery-headers](https://docs.github.com/en/webhooks/webhook-events-and-payloads#delivery-headers)). Key dedupe on `X-GitHub-Delivery` (+ hook ID), so redeliveries are idempotent rather than "new". Keep keys ≥3 days, since redelivery covers "the past 3 days" ([redelivering-webhooks#about-redelivering-webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks)).

**4. The ops retry assumption is false.** "GitHub does not automatically redeliver failed deliveries" ([handling-failed-webhook-deliveries#about-webhook-delivery-failures](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#about-webhook-delivery-failures)). Recovery must be your own scheduled script listing deliveries and calling redeliver ([#handling-delivery-failures](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#handling-delivery-failures)).

**Exactly-once?** No. First-party docs establish sender authenticity, a stable delivery ID, and a 10-second deadline — no ordering or transactional guarantee spanning a receiver crash. Exactly-once business effects are UNVERIFIED; resolve via [#redeliver-a-delivery-for-a-repository-webhook](https://docs.github.com/en/rest/repos/webhooks#redeliver-a-delivery-for-a-repository-webhook). Recommendation: target at-least-once plus idempotency, committing the dedupe record in the same transaction as the side effect.
