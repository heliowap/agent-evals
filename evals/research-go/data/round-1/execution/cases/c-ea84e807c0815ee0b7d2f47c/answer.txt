## Decision

**Change these four things (all documented requirements, not options):**

1. **Verify before parsing, on the untouched bytes.** Signature authenticity evidence is `X-Hub-Signature-256`: an HMAC hex digest of the *request body* computed with your webhook secret and SHA-256 ([delivery headers](https://docs.github.com/en/webhooks/webhook-events-and-payloads#delivery-headers)). Compute it over the raw body and never let a proxy modify payload or headers before verification ([troubleshooting](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#troubleshooting)). Your parse-then-re-serialize step invalidates the digest for whitespace, key order, and unicode escaping — even when the JSON is semantically equal.
2. **Constant-time compare.** GitHub explicitly says never use plain `==`; use `secure_compare`/`hmac.compare_digest`/`crypto.timingSafeEqual` ([validating webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries)).
3. **Respond 2XX in under 10 seconds.** A 25‑second synchronous job exceeds this: GitHub terminates the connection and records the failure, so your *success response never arrives* ([respond within 10 seconds](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds)). Enqueue and return immediately; process asynchronously.
4. **Deduplicate on `X-GitHub-Delivery`, treating redelivery as the *same* event.** Your premise is wrong: the docs state the header "will be the same as in the original delivery" on redelivery ([use the X-GitHub-Delivery header](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header)); the sample script confirms "the GUID is constant across redeliveries of the same delivery" ([redelivery script](https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-repository-webhook#adding-the-script)). Keying on a new identifier is what creates duplicates.

**Correct the recovery plan.** GitHub does **not** automatically redeliver, and a 10‑second timeout counts as failure ([failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#about-webhook-delivery-failures)). Recovery must be your scheduled script using the deliveries REST API, or manual redelivery limited to the **past 3 days** ([redelivering webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks)).

**Exactly-once?** No. GitHub documents authenticity and identifier stability, not delivery-once semantics. Exactly-once across a receiver crash requires the dedupe record and the business effect to commit atomically on your side — UNVERIFIED as documented; resolve by checking whether your store's GUID insert is transactional with the effect, and keep event processing idempotent.
