**Decision: do not deploy as proposed, and do not treat the Permission Model as the sole tenant-isolation boundary.**

**Premise corrections (documented)**
- It "does not protect against malicious code"; it is a "seat belt" for trusted code (https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permissions). The policy says it reduces blast radius of mistakes in trusted code, "not ... a security boundary against intentional misuse or a compromised process" (https://raw.githubusercontent.com/nodejs/node/v24.21.0/SECURITY.md#permission-model-boundaries-permission). Tenant JS is exactly the CWE-653 case the policy calls application-level.
- `--allow-fs-read=/srv/jobs/*.js` is not a `.js` filter: after a `*`, "all subsequent characters will be ignored… `/home/*.js` will work similar to `/home/*`" (https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#file-system-permissions). You grant all of `/srv/jobs` (cross-tenant reads); an existing directory also gains `/*` implicitly.
- Relative symlinks defeat the grant: symlinks are followed outside granted paths, and operators "must ensure that no paths to which access has been granted contain relative symbolic links" (https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#limitations-and-known-issues).
- A pre-opened FD is a bypass: "Using existing file descriptors via the node:fs module bypasses the Permission Model" (https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints).
- `--env-file` loads before initialization and "is not subject to the rules of the Permission Model" (same section). Values become `process.env`, which workers copy (https://nodejs.org/download/release/v24.21.0/docs/api/worker_threads.html#class-worker), so secrets there are exposed to tenant code.
- Audit mode denies nothing; if both flags are passed, `--permission` wins (https://nodejs.org/download/release/v24.21.0/docs/api/cli.html#--permission-audit). Staging audit cannot validate enforcement.
- `process._debugProcess()` can force another same-OS-user Node process to open its inspector, ungated (https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#process_debugprocess-and-cross-process-inspector-activation). FS access also leaks via `node:sqlite` (same page, #file-system-permissions).

**Worker inheritance: UNVERIFIED conflict.** Permissions docs state "The model does not inherit to a worker thread" (https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints); SECURITY.md says workers inherit and modified `execArgv` grants nothing (SECURITY.md, same anchor above). `worker_threads` documents only `execArgv`/option inheritance, not permissions (https://nodejs.org/download/release/v24.21.0/docs/api/worker_threads.html#new-workerfilename-options). Resolve via the v24.21.0 test suite/source before trusting `--allow-worker` (which is Stability 1.1: https://nodejs.org/download/release/v24.21.0/docs/api/cli.html#--allow-worker).

**Recommendation:** isolate tenants with OS-level controls (separate users, containers, seccomp); use the Permission Model only for trusted app hardening, with `permission.has()`/`drop()` (https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#runtime-api). These docs cannot certify tenant isolation.
