**Decision: the design is not sufficient.** Repeatable Read (RR) gives a stable snapshot and, in PostgreSQL, no phantoms — but that is a stronger-than-standard implementation choice, not serial equivalence. The SQL standard merely *allows* phantoms at RR; PostgreSQL disallows them, while still permitting **serialization anomalies** ([Table 13.1](https://www.postgresql.org/docs/18/transaction-iso.html#MVCC-ISOLEVEL-TABLE), [RR section](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). For cross-row read-then-write invariants, RR snapshots can form read/write cycles; the docs warn that enforcing business rules at this level is "not likely to work correctly without careful use of explicit locks" ([applevel-consistency](https://www.postgresql.org/docs/18/applevel-consistency.html)).

**Narrow changes that matter**

1. **Isolation.** Use Serializable for transactions that read *and* write the invariant: it is RR plus nonblocking monitoring that aborts a participant when a cycle could form ([Serializable](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE); [Serializable consistency](https://www.postgresql.org/docs/18/applevel-consistency.html#SERIALIZABLE-CONSISTENCY)). Or keep RR and acquire `SELECT FOR UPDATE`/`LOCK TABLE` **before** the snapshot freezes ([explicit locking](https://www.postgresql.org/docs/18/applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY)).
2. **Retry unit = whole transaction, owned by the application.** PostgreSQL aborts the transaction on `40001`; the retry must re-run all decision logic, because that logic reads data the new transaction must re-read ([RR](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). "PostgreSQL does not offer an automatic retry facility" ([Serialization Failure Handling](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html#MVCC-SERIALIZATION-FAILURE-HANDLING)). Retrying only the failed statement cannot replay the decision.
3. **Unique violations do not belong in an unconditional bucket.** Retry `40001` unconditionally, and consider `40P01`; retry `23505`/`23P01` only with care, since they "might represent persistent error conditions rather than transient failures" — e.g., a genuine concurrent duplicate key insert ([Serialization Failure Handling](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html#MVCC-SERIALIZATION-FAILURE-HANDLING); class 23 is Integrity Constraint Violation, [Appendix A](https://www.postgresql.org/docs/18/errcodes-appendix.html#ERRCODES-TABLE)).

**Three-attempt promise: no.** Documentation states retries do not guarantee completion, high contention "may take many attempts," and a conflicting prepared transaction can prevent progress until it ends ([Serialization Failure Handling](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html#MVCC-SERIALIZATION-FAILURE-HANDLING)). Any bounded-attempt guarantee is **UNVERIFIED/unsupportable**; resolve by measuring actual retry distributions under production contention. If replicas exist, Serializable protection does not extend to hot standby/logical replicas ([warning](https://www.postgresql.org/docs/18/applevel-consistency.html#SERIALIZABLE-CONSISTENCY)).
