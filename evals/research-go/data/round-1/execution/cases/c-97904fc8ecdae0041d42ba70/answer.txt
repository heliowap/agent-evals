## Decision

**Use long-form `depends_on`; the short form cannot express this.** Short syntax only guarantees start order and explicitly "does not wait for dependency services to be 'healthy'" ([services reference](https://docs.docker.com/reference/compose-file/services/#short-syntax-1)). Correct the premise: the current API definition must be rewritten.

Recommended conditions (all supported at 2.18.0):
- `api.depends_on.db: {condition: service_healthy, restart: true}`
- `api.depends_on.migrate: {condition: service_completed_successfully}`

`restart: true` was introduced in Compose **2.17.0**, so it is available; `service_completed_successfully` and `service_healthy` likewise ([long syntax](https://docs.docker.com/reference/compose-file/services/#long-syntax-1)).

## What each concern covers
- **Container startup:** Compose creates services in dependency order; it "does not wait until a container is 'ready', only until it's running" ([startup order](https://docs.docker.com/compose/how-tos/startup-order/#control-startup)).
- **Health/readiness:** only `service_healthy` gates on the `healthcheck` ([startup order](https://docs.docker.com/compose/how-tos/startup-order/#example)).
- **Migration completion:** `service_completed_successfully` blocks API start until the one-shot exits 0.
- **Explicit operator restart:** `restart: true` restarts the dependent "if db is updated or restarted due to an explicit Compose operation, for example `docker compose restart`" ([startup order](https://docs.docker.com/compose/how-tos/startup-order/#example)).
- **Runtime restart:** **not covered.** The docs state this "excludes automated restart by the container runtime after the container dies" ([long syntax](https://docs.docker.com/reference/compose-file/services/#long-syntax-1)). `restart: always` on the database only restarts the database.

## Telemetry proposal — blocked at 2.18.0
`required: false` was **introduced in Compose 2.20.0**, so it cannot be used without upgrading ([long syntax](https://docs.docker.com/reference/compose-file/services/#long-syntax-1)). Alternatives: upgrade, use `profiles`, or omit it from `depends_on`.

## Ready-to-serve promise
**No.** `depends_on` is a startup-ordering mechanism; no fetched page documents ongoing health monitoring or reconnection after later failures. Promising continuous readiness is UNVERIFIED — resolve with an app-level retry/connection-pool design and a second healthcheck consumer.
