**Authenticity evidence (documented).** Only the HMAC signature proves GitHub origin. GitHub computes an HMAC hex digest over the raw payload with your webhook secret and sends it in `X-Hub-Signature-256` (starts with `sha256=`); the header is absent if no secret is set ([validating](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#about-validating-webhook-deliveries)). Verify against the **unmodified raw body** as UTF-8, and never use plain `==` — use a constant-time compare ([same page](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries#validating-webhook-deliveries)). So your parse-then-re-serialize flow and ordinary `==` are both wrong: the changed bytes make the digest mismatch, and `==` enables timing attacks. Redeliveries carry the same secret-signed payload, so a valid signature is authentic but **not** proof of non-duplication.

**Identifier behavior (documented).** Use `X-GitHub-Delivery` to ensure each delivery is unique per event; on a requested redelivery this header is **the same** as the original ([best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header)). GitHub's own redelivery script dedups on `guid`, "constant across redeliveries," and only re-sends when no attempt for that GUID succeeded ([redelivery script](https://docs.github.com/en/webhooks/using-webhooks/automatically-redelivering-failed-deliveries-for-a-repository-webhook#about-automatically-redelivering-failed-deliveries)). **Correct the premise:** the team's expectation of a new identifier is wrong; key dedup on the delivery GUID, not a changing delivery-attempt ID.

**Timing/retry assumptions (documented).** Respond 2XX within 10 seconds or GitHub terminates and marks failure — so move the 25-second job off the request path to a queue and ack immediately ([best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#respond-within-10-seconds)). **Correct the outage premise:** GitHub does **not** automatically redeliver failed deliveries; you must redeliver manually or on a schedule, and only deliveries from the **past 3 days** are available ([handling failures](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries#about-webhook-delivery-failures), [redelivering](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks#about-redelivering-webhooks)).

**Exactly-once.** No. These mechanisms give at-least-once/authenticity and replay protection, not exactly-once; across a receiver crash a duplicate side effect is possible.
