**Verdict: the proposed design is not sufficient.** Two premises are wrong: statement-level retry, and unconditional retry of unique violations.

**Isolation (documented facts)**
- The SQL standard defines levels by prohibited phenomena; PostgreSQL's Repeatable Read blocks phantom reads, which the standard permits because it "only describes the minimum protections each isolation level must provide" ([transaction-iso.html#XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). Only Serializable guarantees an outcome equal to some serial order ([#XACT-SERIALIZABLE](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)).
- The docs state directly: at Repeatable Read, "Attempts to enforce business rules by transactions running at this isolation level are not likely to work correctly without careful use of explicit locks" ([#XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). A stable snapshot plus no phantoms does not close read/write-dependency cycles ([applevel-consistency.html#APPLEVEL-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#APPLEVEL-CONSISTENCY)).

**Retry ownership and unit**
- Recommended: the application/framework owns retrying; PostgreSQL "does not offer an automatic retry facility, since it cannot do so with any guarantee of correctness." The unit is the whole transaction "including all logic that decides which SQL to issue and/or which values to use" ([mvcc-serialization-failure-handling.html](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Repeatable Read failures roll back the transaction, requiring restart "from the beginning" ([#XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)); a failed transaction rejects further statements (25P02, [errcodes-appendix.html#ERRCODES-TABLE](https://www.postgresql.org/docs/18/errcodes-appendix.html#ERRCODES-TABLE)). So replaying one statement cannot silently re-run prior decision logic.

**Error classes**
Retry 40001 unconditionally; consider 40P01 (deadlock). For 23505, "more care is needed... they might represent persistent error conditions" — retry only if the code inspected the cause and the value was chosen from prior reads. Note Serializable can raise unique violations even after an explicit existence check ([#XACT-SERIALIZABLE](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)).

**Three-attempt promise: no.** Docs: retry "does not guarantee that the retried transaction will complete; multiple retries may be needed," possibly "many attempts," and a conflicting prepared transaction can block progress indefinitely. A contractual ≤3-attempt guarantee is UNVERIFIED; resolve with measured contention data plus a bounded-retry-plus-shed policy, not a documented promise.

**Recommendation:** use Serializable for all writers/consistent readers (or keep Repeatable Read with explicit locks acquired before the snapshot freezes), and note Serializable protection does not extend to hot standby/logical replicas ([#SERIALIZABLE-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#SERIALIZABLE-CONSISTENCY)).
