## Decision: not sufficient — change the isolation basis, the retry unit, and the retry bucket

**The premise is wrong.** Repeatable Read gives a stable snapshot and (stronger than the SQL standard's minimum for this level) no phantoms, but PostgreSQL explicitly warns that this view "will not necessarily always be consistent with some serial (one at a time) execution," and that enforcing business rules at this level "is not likely to work correctly without careful use of explicit locks" ([transaction-iso #XACT-REPEATABLE-READ](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). Stable snapshots plus no phantom reads do **not** equal serial execution; serialization anomalies remain possible. The standard only sets *minimum* protections per level, and PostgreSQL's RR deliberately exceeds them ([transaction-iso](https://www.postgresql.org/docs/18/transaction-iso.html#TRANSACTION-ISO)).

**Correct isolation for "read invariant, write different rows":** use Serializable for all such reads/writes, or keep Repeatable Read and take explicit locks (`SELECT FOR UPDATE`/`LOCK TABLE`) on everything the check depends on, obtaining locks *before* the snapshot freezes ([applevel-consistency #SERIALIZABLE-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#SERIALIZABLE-CONSISTENCY), [#NON-SERIALIZABLE-CONSISTENCY](https://www.postgresql.org/docs/18/applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY)). Serializable is the narrow change if you want the database to detect the unsafe interleavings.

**Who retries, and what:** the application, never the server — "PostgreSQL does not offer an automatic retry facility" ([serialization-failure-handling](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). The retry unit is the **complete transaction, including all logic that decides which SQL to issue and/or which values to use**. Statement-level retry cannot work: a serialization error aborts the transaction (state `25P02 in_failed_sql_transaction`, [errcodes-appendix](https://www.postgresql.org/docs/18/errcodes-appendix.html#ERRCODES-TABLE)), so the earlier decision is not replayed — the wrapper must restart from `BEGIN`.

**Unique violations do not belong in an unconditional bucket.** `40001` may be retried unconditionally, and `40P01` often; but `23505 unique_violation` / `23P01 exclusion_violation` "might represent persistent error conditions," so retry only after classifying the cause ([serialization-failure-handling](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html); codes in [errcodes-appendix](https://www.postgresql.org/docs/18/errcodes-appendix.html#ERRCODES-TABLE)).

**Three-attempt promise: no.** Documentation states retry "does not guarantee that the retried transaction will complete; multiple retries may be needed" and under high contention "many attempts"; a conflicting prepared transaction can block progress entirely ([serialization-failure-handling](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)). Recommend bounded retries with backoff and an explicit failure signal instead of a commit-within-three guarantee. Any such promise is **UNVERIFIED**; resolve via load-testing under your contention profile.
