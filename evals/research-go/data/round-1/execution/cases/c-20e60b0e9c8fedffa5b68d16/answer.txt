**Decision: do not deploy as proposed.** The Node.js docs do not support certifying tenant isolation, and several stated assumptions are factually wrong.

**Cannot certify**
The Permission Model "does not protect against malicious code"; it is "a 'seat belt'" for trusted code and "Malicious code can bypass the permission model and execute arbitrary code" ([permissions.html#permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permissions)). SECURITY.md states untrusted code exposing Node APIs is an application-level issue (CWE-653), not a Node vulnerability, and "Workers inherit the permission restrictions of their parent process" — while `permissions.html` says the opposite: "the model does not inherit to a worker thread." **Conflicting evidence — UNVERIFIED.** Do not assume worker inheritance; resolve by testing your pinned v24.21.0 build and asking nodejs/security-wg.

**Assumptions that must change**
- **Wildcard is broader than written.** "After passing a wildcard character (\*) all subsequent characters will be ignored," so `/srv/jobs/*.js` behaves as `/srv/jobs/*` — the whole tree, not just `.js` files ([#file-system-permissions](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#file-system-permissions)). List exact files instead; entrypoints are already implicitly readable.
- **Relative symlinks.** "Relative symbolic links may allow access to arbitrary files and directories… you must ensure that no paths to which access has been granted contain relative symbolic links" ([#limitations-and-known-issues](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#limitations-and-known-issues)). Your premise ("job directories may contain relative symbolic links") is disqualifying.
- **The pre-opened FD is not covered.** "Using existing file descriptors via the node:fs module bypasses the Permission Model" ([#permission-model-constraints](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#permission-model-constraints)).
- **--env-file is pre-permission.** `--env-file` reads "before environment initialization," so it is "not subject to the rules of the Permission Model"; its contents — including `NODE_OPTIONS`, which is "parsed and applied" — become visible to tenant code ([cli.html#--env-filefile](https://nodejs.org/download/release/v24.21.0/docs/api/cli.html#--env-filefile)). Never let tenants write it.
- **Inspector escape.** `process._debugProcess(pid)` "is not gated by the kInspector scope or any other Permission Model scope" ([#process_debugprocess](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#process_debugprocess-and-cross-process-inspector-activation)); use separate OS users.
- **Staging ≠ production.** `--permission-audit` denies nothing; with `--permission` it is overridden ([#audit-mode](https://nodejs.org/download/release/v24.21.0/docs/api/permissions.html#audit-mode)).

**Appropriate use:** seat-belt oversight of trusted application code — `permission.has()`, irreversible `permission.drop()`, and audit-mode discovery.

**Conclusion:** No — these documents explicitly decline to make the Permission Model a malicious-code boundary. Use OS-level isolation (users, containers, seccomp) for tenants, per [SECURITY.md#permission-model-boundaries](https://github.com/nodejs/node/blob/v24.21.0/SECURITY.md#permission-model-boundaries---permission).
