## Verdict: insufficient — two correct premises, three defects

**Premises.** Repeatable Read does give a transaction a stable snapshot "as of the start of the first non-transaction-control statement," and PostgreSQL's RR additionally prevents phantoms — stronger than the SQL standard's minimum, which allows phantoms at RR ([Table 13.1](https://www.postgresql.org/docs/18/transaction-iso.html#MVCC-ISOLEVEL-TABLE)). But the standard's serializability guarantee is not implied: RR is Snapshot Isolation, and serialization anomalies remain "Possible" ([same table](https://www.postgresql.org/docs/18/transaction-iso.html#MVCC-ISOLEVEL-TABLE)). The docs warn that enforcing business rules at RR is "not likely to work correctly without careful use of explicit locks," because a stable view "will not necessarily always be consistent with some serial ... execution" ([13.2.2](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ)). Reading a cross-row invariant and then updating *different* rows is exactly the read/write-conflict cycle described in [13.4](https://www.postgresql.org/docs/18/applevel-consistency.html#APPLEVEL-CONSISTENCY) (write skew).

## Narrow corrective changes

1. **Use SERIALIZABLE for the invariant path** — SSI adds non-blocking monitoring and rolls back one transaction instead of permitting an anomalous commit ([13.2.3](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)). If RR must stay, take `SELECT FOR UPDATE`/`LOCK TABLE` **before** the snapshot freezes ([13.4.2](https://www.postgresql.org/docs/18/applevel-consistency.html#NON-SERIALIZABLE-CONSISTENCY)). Documented caveat: this protection does not extend to hot standby or logical replicas ([13.4.1 warning](https://www.postgresql.org/docs/18/applevel-consistency.html#SERIALIZABLE-CONSISTENCY)).
2. **Owner: the application.** PostgreSQL offers no automatic retry "since it cannot do so with any guarantee of correctness."
3. **Unit: the whole transaction**, "including all logic that decides which SQL to issue and/or which values to use." Statement-level replay is invalid: errors abort the transaction (SQLSTATE 25P02 `in_failed_sql_transaction`, [Appendix A](https://www.postgresql.org/docs/18/errcodes-appendix.html#ERRCODES-TABLE)), and `ROLLBACK TO SAVEPOINT` restores the transaction without clearing its old snapshot, so earlier decisions cannot be re-derived from fresh reads ([ROLLBACK TO SAVEPOINT](https://www.postgresql.org/docs/18/sql-rollback-to.html)).
4. **Error buckets:** retry 40001 unconditionally; 40P01 is "advisable"; for 23505/23P01 "more care is needed ... since they might represent persistent error conditions" — classify by cause, never blanket-retry. Overlapping serializable transactions can raise unique violations even after pre-checking ([13.2.3](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-SERIALIZABLE)).
5. **Three-attempt promise: no.** "Multiple retries may be needed"; under very high contention, completion "may take many attempts"; a conflicting prepared transaction may block progress indefinitely ([13.5](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html#MVCC-SERIALIZATION-FAILURE-HANDLING)). UNVERIFIED: any documented attempt bound. Resolve by instrumenting retry counts and setting an operational SLO, not a correctness guarantee.
