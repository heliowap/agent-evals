# Go-only 72-run researcher comparison: harness and design findings

## Answer

Use a new standalone, per-case private harness; freeze six tasks, six atomic checks each, protocol, source snapshots, and a constrained-randomized 12-block schedule before the first inference. Run one candidate at a time, with the first scheduled DeepSeek Go LOW case serving as the counted access gate. Compare qualified correctness/citation/compliance first and successful launch-to-exit latency second, using paired differences and task-cluster uncertainty. Labels, deny rules, stdout, and historical no-prompt verification are insufficient proof of effective upstream effort, actual tool exposure, complete usage, or new isolation. These are protocol recommendations grounded in the sources below, not results from a new benchmark. [C1–C3, D1–D8, N1; user research contract]

## 4. Equal budgets and counted access gate

**Proposed frozen budgets:** one candidate at a time; **≤400 visible words** across all assistant-visible text (including pre-fetch commentary), excluding reasoning/tool bodies and link destinations; `steps: 8`; hard **180-second launch-to-exit** deadline; zero caller retries, substitutions, warmups or smoke cases. Use a deterministic documented Markdown/whitespace counting rule and preserve both raw/visible counts. Do not change these limits by model or after observing answers. [user requested limits; D6; OLD/collect.py:51–52]

A correction to “8-step tool ceiling”: V2 `steps` limits **model steps**, not individual tool calls. At step 8 tools are removed and final text is requested; a Code Mode call can make several nested fetches. Eight steps provides seven potentially tool-producing rounds and one final round, compared with old six; this is a protocol choice providing more room for the more substantial suite, **not a demonstrated adequate cap for the unseen tasks**. Specify/count fetches and execute calls separately; do not invent a built-in eight-fetch ceiling. The actual task inventory may justify a separate generous total-fetch limit before freeze, but it must not silently conflate these units. [D6, D8; OLD/report.md:43; user task-substance contract]

At 72 × 180 seconds, case deadlines alone total **12,960 seconds = 216 minutes = 3 h 36 min**; setup, collection and grading are additional. A 10–30-second typical-case assumption is only a planning hypothesis supplied by the task, not verified for these new tasks. Old successful task times were much shorter than the deadline but came from different content/conditions. No runtime guarantee follows. [arithmetic from proposed design; OLD/report.md:11–19,58]

Freeze all 72 rows first. Schedule row 1 must be a **real task/repetition DeepSeek Go LOW** case, not a metadata prompt or smoke. It contributes its result/usage/time to the 72-case study. Do not edit workspace/privacy, change routes, switch OpenRouter, or spend another inference to “confirm.” A stopped study is **1 attempted / 72 planned**, not a completed 72-run comparison. Current restriction persistence is **UNVERIFIED until this counted case**. [FAIL/report.md:22–28,41–45; user gate contract]

A different first-case failure also does not constitute successful access. Preserve/classify it and stop pending parent decision instead of silently retrying or bypassing the gate. ## 5. Schedule: interleaved paired blocks, constrained randomization

**Proposed design:** 6 fixed tasks × 2 repetitions = **12 task/repetition blocks**. Every block contains each of the six configurations once; blocks run contiguously, one candidate at a time. Constrained seeded randomization gives row 1 DeepSeek LOW as above while randomizing the rest. Publish seed, algorithm, full row order, opaque artifact IDs and schedule hash before inference. Avoid six model-major batches and do not allow progress/outcomes to choose order. [N1; user exact factorial/gate contract]

A practical counterbalance is two sets of six six-position rows: use a randomized Latin-square-style arrangement so each configuration occupies each position twice across 12 blocks, randomize task-to-row assignment within each repetition, and constrain the first row/first position to DeepSeek LOW. Separate a task's second repetition from its first by the intervening first-repetition blocks. Inspect the realized position counts/pair order and record the constraint; this is **not unconstrained random order** and does not eliminate every carryover effect. No concrete seed/schedule is created in this research file because the exact tasks are parent-owned and not inspected here. [N1; protocol proposal]

Use fresh empty local sessions/DB/cache per case, explicit `warming:false`, identical source-format choices/catalog/system, and the same private-startup treatment. That controls local history and simultaneous candidate contention, **not provider caches or remote load**. Go docs expressly optimize routing/caching using stable session IDs; old MAX A received cache reads while B did not. Do not add cache-busting junk, undocumented bypass headers, temperature perturbations or prewarming calls. Record actual cache-read/write tokens, first/later chronological case, position, repetition, UTC start/end, relevant provider peak/off-peak classification, host load/concurrent controller work, fetch duration/status and source hash. [D11–D12; OLD/report.md:35–45,58]

Keep collection/grading and other controller-heavy work out of candidate timing windows where feasible; preserve one-at-a-time concurrency with explicit start/end non-overlap evidence. Record interruptions/pauses instead of rescheduling based on quality. If metadata/protocol/source drift is material during the study, report affected blocks and apply a predeclared pause/stop rule; do not restart selected cells. ## 6. Timing, retries, termination and honest statuses

Primary speed measure: monotonic time immediately before process launch through observed process exit, including CLI/private-server/config startup, model work, fetches and any allowed internal retries. Save UTC timestamps separately for pairing and source/cache/backend context. Secondary measure: earliest assistant-created to latest terminal assistant-completed time; if missing completion, report unavailable/unfinished rather than substituting zero. Neither quantity is automatically time to first token or model generation throughput. [OLD/run.py:29–30,39–52,61; OLD/collect.py:50; D9 `Session.Message.Assistant.time`]

Enforce the wall deadline outside OpenCode with the owned process group, drain stdout/stderr, record exact termination, await child exit and verify owned descendants are gone without stopping unrelated processes. No runner implementation is supplied here. Provider request timeouts are not a process deadline: D4 documents five-minute header/chunk defaults, optional whole-request timeout, and up to three retries of timeout failures. C1 has no per-run timeout/retry-disable flag. [D4; C1; OLD/run.py:30–56]

Preferred interpretation for a user-facing quality/latency recommendation: **no caller retries; retain default internal retry behavior identically**, bounded by 180 seconds, and report observable retry count/delay separately. That keeps each of 72 cells one scheduled research invocation, although it may involve more physical HTTP attempts. If the parent instead requires first-attempt-only behavior, that policy must be settled before freeze and supported by a verified built-in control/source; this research did not verify such a control. Native retry hooks exist but require a plugin, disallowed here. [D4, D13; user exact-run/no-plugin contract]

Do not copy the old stream-chunk retry killer as proof of zero internal retries: it scans arbitrary byte chunks for substrings and can miss split events or react to ordinary output. Parse complete JSON/SSE records with persistent buffering and corroborate durable assistant retry fields/logs. Stopping after a visible retry announcement is not proof the next wire attempt never began. Without wire-level logging label physical HTTP attempt count **UNVERIFIED**, even if no retry event appears. [OLD/run.py:31–49; OLD/report.md:49; D9 `Session.Message.Assistant.retry`, `Session.Message.Assistant.Retry`; D13]

Classify `completed`, `timeout`, `provider_error`, `access_gate_error`, `tool_error`, `harness_error`, `retry_stopped` (only if chosen), `step_limit/incomplete`, and `not_run` distinctly. Exit code 0 is not enough: check terminal DB finish, errors/retries, idle/end state and nonempty answer. Reaching step cap can produce a stop-shaped summary that is still incomplete; semantic qualification comes later. Never rank an empty/partial response as a fast success. [D6; D9 `Session.Message.Assistant.finish/error`; OLD/verify.py:95–106; FAIL/report.md:28]

## 9. Source-entailment scoring and blinded adjudication

**Proposed frozen rubric:** six atomic required checks per task, each with requirement wording, accepted alternatives, primary URLs, exact frozen source excerpt/location and criticality. Each response/check receives exactly one status: `supported`, `contradicted`, `missing`, or `unverifiable`. Keep factual correctness and citation entailment distinct: a true required answer without an attached acceptable supporting citation can be factual credit but does not qualify as cited success. Ambiguous source/wording is not automatic binary failure or success. [user scoring contract; OLD/verify.py:126–139,175; OLD/report.md:21–29]

Every supported/contradicted/unverifiable judgment needs an answer quote, specific claim-to-citation mapping, source quote/location and short entailment rationale.
